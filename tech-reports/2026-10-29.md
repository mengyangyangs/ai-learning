# 每日 AI 技术报告 · 2026-10-29

**日期：** 2026 年 10 月 29 日（星期四）

## 一、先定界：Harness 到底是什么，又不是什么

一个基础模型本质上是无状态的函数：输入 token，输出 token。它自己不会开文件、跑测试、记得上一会话，更不知道自己刚才那步做成了没有。

**Agent = Model + Harness。** Harness 是除模型之外的一切运行时：循环、工具、上下文拼装、记忆、权限、编排、扩展面。LangChain 的表述最值得记住：**如果你不是模型，你就是 Harness。**

arXiv 2609.00006 进一步划了四条边界，避免把词用混：

- Harness 不是脚手架的同义词的精确版：脚手架偏结构代码，Harness 是交付出来的完整运行时（含 UI、权限、插件生态）。
- Harness 不是通用 Agent 框架：框架是你 import 进来建 Agent 的库，Harness 是你进去工作的运行时——2026 年两者正在互相靠拢，但方向是 Harness 自己变成可 import 的 SDK，而不是运行时去 import 旧框架。
- Harness 不是评测 Harness：前者包住模型让它干活，后者包住 Agent 给它打分，包裹方向正好相反。
- Harness 不是编排器：编排器（如 meta-harness）在 Harness 之上协调多个 Harness，自己没有编辑循环。

这个区分不是咬文嚼字。它决定了排障时该改哪里：模型答错了，不一定是模型问题；更可能是循环没给上限、工具描述写错、关键规则在压缩后丢了、或者根本没有“做完”的硬标准。

## 二、从行为倒推设计：LangChain 的方法

LangChain《The Anatomy of an Agent Harness》的核心方法不是先列技术清单，而是**先写出想要的行为，再倒推 Harness 必须提供什么**：

| 想要的行为 | 倒推出来的 Harness 部件 |
|---|---|
| 能记住东西 | 文件系统、记忆文件 |
| 能自主解题 | bash / 代码执行工具 |
| 执行要安全 | 沙箱、权限 |
| 能持续学习 | 记忆文件 + 搜索 |
| 能长期自主执行 | 文件系统 + git + Ralph Loop + 规划 + 自验证 |

这张表的好处是可证伪：每加一个部件，都要能说出它对应哪种行为、以及去掉它会丢哪种行为。反过来，凡是说不出对应行为的部件，都是可疑的复杂度。Anthropic 在长时应用一文里用的正是同一原则，只是更狠：模型升级后，逐个拆掉部件重测，只保留在当前模型下仍然 load-bearing（承重）的部件。

一个反直觉的证据：LangChain 举例说，只改 Harness 就能把同一模型在 Terminal Bench 上的排名从 30 名外提升到前 5。这类个案不能推广为“Harness 总是比模型重要”，但它足以说明：**报模型名而不报 Harness，等于没报完整配置。**

## 三、长时任务的真正敌人：不是“不够聪明”，是“接不上”

Anthropic 两篇长时文章合起来讲的是同一个敌人：会话一断，任务就断。

### 1. 旧版 Harness：Initializer + Coding Agent + 文件即记忆

- 第一个会话由初始化 Agent 准备环境：启动脚本、进度文件、功能清单、初始 git 提交。
- 之后每个编码会话只做一件事：读进度、选一个未通过的功能、实现、自己验证、提交、更新进度。
- 功能清单一开始全部标记未通过，Agent 只能改通过状态，不能删测试、不能把没做完说成做完了。清单用 JSON 而不用 Markdown，据称模型更不容易顺手改写 JSON 的结构。
- 对 Web 应用，只跑单元测试不够，必须像真人用户那样用浏览器走端到端流程。

这套设计针对两个真实失败：一次想把整个应用做完、做到一半上下文用完留个半成品；以及后一个会话看到已有进展就直接宣布大功告成。解法不在提示词里多写一句“请认真”，而在文件、清单、git 提交这些**会话外也存在**的东西里。

### 2. 新版 Harness：Planner → Generator ↔ Evaluator

Anthropic《Harness design for long-running application development》把结构升级为三 Agent：

- **Planner：** 把 1–4 句话扩成完整产品规格，但刻意不写死实现细节——前期错写细节会向下级联，宁可约束“要交付什么”，把路径留给下游。
- **Generator：** 按 sprint 一次做一个功能，自评后再交给 QA。
- **Evaluator：** 用 Playwright MCP 真正点开正在跑的应用，按产品深度、功能、视觉设计、代码质量等标准打分；任一标准低于硬阈值，sprint 就失败、退回重做。
- **Sprint 合同：** 每个 sprint 开始前，Generator 与 Evaluator 先谈判“什么算做完、怎么验证”，谈妥了再写代码。沟通只靠文件：一个写、另一个读了再回写。

两个关键失败模式值得单列：

- **Context anxiety（上下文焦虑）：** 模型临近自以为的上下文上限就提前收尾。压缩（把旧历史摘要后继续）保住了连续性，但给不了干净起点，焦虑仍在；上下文重置（全新会话 + 结构化交接产物）给干净起点，但要付编排与 token 成本。在 Sonnet 4.5 上重置是必需的，到 Opus 4.5/4.6 上该行为缓解，作者就直接去掉了重置——**Harness 部件的去留，取决于当前模型，不是一劳永逸的。**
- **自我评价不可靠：** 生成者会自信地夸自己的平庸作品，尤其在设计这种没有二值检验的主观任务上。把“做”与“判”分开、再用 few-shot 评分示例把 Evaluator 校准成怀疑型，比让生成者自我批评更易调通。前端实验的四条标准是设计质量、原创性、工艺、功能性，并加重前两项以压制模板化的“AI slop”。

对照实验要连成本一起读：同一句“做一个 2D 复古游戏制作器”，单 Agent 约 20 分钟、约 9 美元，但核心玩法是坏的（实体不响应输入）；三 Agent Harness 约 6 小时、约 200 美元，产出 16 个功能、10 个 sprint，且玩法能跑。**20 倍成本换来的不是“更好一点”，而是“从不能用变能用”——但这仍是单次实验，不能当作通用成本倍数。** 后续 DAW 一例（约 4 小时、124 美元）里，QA 仍抓住了“音频录制只是 stub、片段不能拖拽/分割”这类核心缺口，说明 Evaluator 的价值不在“锦上添花”，而在“最后一公里”。

## 四、OpenAI Agents SDK：两种编排，权限与历史是分水岭

OpenAI Agents SDK 把多 Agent 编排归为两条路线，选错路线，后面的权限与历史问题全都会错位：

### 1. Agents as tools：管理者不交权

管理者用 `agent.asTool({ toolName, toolDescription })` 把专家挂成工具。管理者始终掌握对话和最终答案，适合要统一护栏、汇总多专家结果的场景。专家只返回结果，不接管用户对话；主 Agent 默认只拿到摘要，看不到专家的探索过程——这是上下文隔离的收益，排障时要靠 trace 补。

### 2. Handoff：分诊员交出整个对话

分诊 Agent 把对话交给专家，专家此后直接对用户负责。在模型看来，handoff 本身就是一个工具，如 `transfer_to_refund_agent`，描述写不清就会路由错。`handoff()` 可配 `inputType`、`onHandoff`、`inputFilter`、`isEnabled` 等。

**权限上最容易写错的三点：**

1. `isEnabled` 在模型返回参数之前评估，**不能用来审批参数里的值**。依赖参数值的授权必须在 `onHandoff` 开头做，且失败要抛异常而不是返回——回调正常返回后，SDK 就会继续交接。
2. 输入护栏只对链上第一个 Agent 跑，输出护栏只对最终产出 Agent 跑；中间环节要靠工具护栏。**而工具护栏不适用于 handoff 调用本身，也不直接适用于 `asTool()`**——不要以为“挂了护栏”就等于“交接也被护住了”。
3. `inputType` 是模型生成的路由元数据（如 reason、priority），不是应用状态。真正的可信状态要放 `RunContext`。**绝不能把模型生成的 reason 当成授权或账户状态的事实来源。**

**历史上两者的差别是根本性的：**

- Handoff 默认把**全部历史**交给接收方。`inputFilter`（如内置 `removeAllTools`）可以去掉工具调用项，但官方文档明确警告：它不会清除已经抄进普通消息或嵌套历史摘要里的工具参数与结果。接收方及其模型提供方，都应被视为已收到被转发历史的接收者。
- Agents as tools 默认**不共享历史**，只共享结果。隔离是默认的，代价是主 Agent 对专家过程一无所知。

一句话选型：专家该直接对用户说话、且有自己的指令与模型时，用 handoff；管理者要保留最终答案、统一护栏、汇总多路结果时，用 agents as tools。两者可以混用：分诊先 handoff 给专家，专家再把有边界的子任务以 agents as tools 交出去。

## 五、arXiv 2609.00006：11 个编码 Agent 的源码审计

这是目前最系统的 Harness 源码审计：2026 年 7 月版，作者 Barbaste 等，语料约 400 万行 Python / TypeScript / Rust，对象是 Claude Code、Codex CLI、Gemini CLI、Mistral Vibe、OpenHands、Aider、Mini-SWE-Agent、Hermes、Pi、OpenCode、OpenClaw 共 11 个，Omnigent 作为 meta-harness 对照点。论文明确声明：**不做基准排名，只做结构比较。**

### 七个标准子系统：最小形与最大形

| 子系统 | 角色 | 最小形 | 最大形 |
|---|---|---|---|
| Agent loop（循环） | 推理与动作交替，管停止条件与失败恢复 | Mini-SWE-Agent：单 bash 工具的线性 while | OpenHands：事件溯源持久事件日志 + 并行动作批 |
| LLM integration（模型接入） | 讲厂商协议、拼提示词、管缓存/思考/路由 | Mini-SWE-Agent：一次 LiteLLM 调用 + 一个 Jinja 模板 | Hermes：5 种自有传输 + 29 个 provider 配置；Codex：服务端下发模型目录 |
| Tools & actions（工具与动作） | 定义并执行 Agent 能做的事，文件编辑为先 | Mini-SWE-Agent：只有 bash | Claude Code：43 个带类型工具 + 延迟加载；Codex：工具调用当 V8 代码执行 |
| Memory & context（记忆与上下文） | 配给上下文窗口，跨轮次与跨会话持久化知识 | Mini-SWE-Agent：无界线性历史 | Codex：Agent 自维护跨会话记忆管线；Gemini CLI：图式上下文蒸馏 |
| Safety & permissions（安全与权限） | 决定什么能跑、什么要问、什么禁止，隔离执行 | Mini-SWE-Agent：只有成本与步数上限 | Codex：策略规则 + LLM 审批复核 + 三平台 OS 沙箱 |
| Orchestration（编排） | 派生与协调子 Agent，连接其他 Agent | Aider：刻意缺席（单 Agent 设计） | Claude Code：递归组合；Omnigent：跨厂商协调（meta 层） |
| Extensibility（扩展性） | 让用户与生态加能力：配置、钩子、技能、插件、MCP | Mini-SWE-Agent：结构类型（Python protocols） | Pi：一切皆扩展运行时；Codex：市场分发插件 |

### 两个“缺席”比“拥有”更说明问题

经三倍语料扩增仍成立的发现：

1. **没有一个运行时导入通用 Agent 框架。** LangChain、LangGraph、AutoGen、CrewAI 等全都不在 11 个运行时的依赖里；Gemini CLI 连 Google 自家的都没用。现场跑的全是手写异步循环。
2. **没有一个用向量嵌入检索代码。** 靠的是 ripgrep、tree-sitter、glob、自动发现的 Markdown 上下文文件等确定性检索。向量检索只出现在个别系统的对话记忆侧，不是代码检索的主 substrate。

扩展标准上，SKILL.md 以 9/11 领先 MCP 的 8/11，ACP 为 6/11；钩子到 7 月已是 9/11 系统的用户级扩展面，Codex 的钩子事件名与 Claude Code 逐字相同——论文称之为“趋同变模仿”。

### 下限与上限之间，差的是什么

Mini-SWE-Agent 约 100 行就覆盖了七个子系统的最小形，论文称其 SWE-Bench Verified 成绩与大三个数量级的系统在同一范围——但模型、日期、部署配置都不同，**不可直接横向排名**。生产系统多出来的代码，主要花在安全、恢复、成本管理、扩展性和平台面，而不是单纯的任务完成率。换句话说：最小 Harness 能跑通任务，生产 Harness 要回答的是“跑偏了怎么办、跑贵了怎么办、被利用了怎么办、换人接手怎么办”。

一个可直接抄的模式是 Hermes 的 **verify-on-stop 护栏**：若一轮改了代码却没有新的验证证据，就把纯文本收尾改写为继续执行——等于把反思循环从循环内移到停止条件上，成本更低。这比在提示词里写“请认真检查”可靠，因为它在模型上下文之外、由 Harness 强制执行。

## 六、把六个部件对照一个具体 Agent：以 Claude Code 为例

把草稿里的六个部件（循环、工具、上下文、记忆、子 Agent、停止与验证），对照 Claude Code 公开的配置约定过一遍，内 Harness 与外 Harness 就分得清了：

| 部件 | 内 Harness（厂商自带） | 外 Harness（用户自己搭） |
|---|---|---|
| 循环 | Gather–Act–Verify 循环，步数与成本上限 | ——（用户一般不改循环本身，改的是触发它的规则） |
| 工具 | 43 个带类型工具，延迟加载；只读可并行、写操作串行 | `.mcp.json` 接入的 MCP 工具；技能里带的脚本工具 |
| 上下文 | 会话开始加载 CLAUDE.md，压缩时重注入关键规则 | CLAUDE.md 本身（企业 → 用户全局 → 父目录 → 项目 → 本地多层拼接，不是覆盖）；技能只在触发时加载全文（渐进披露） |
| 记忆与状态 | 会话记录、会话树 | 项目指令文件 + Agent 自写的状态文件 + git 历史；`~/.claude/projects/` 一类会话轨迹文件本身就是审计线索 |
| 子 Agent | Task 工具派生专家，上下文隔离、只回摘要 | `.claude/agents/<name>.md` 定义的专家：指令、可用工具、触发条件 |
| 停止与验证 | 权限模式、沙箱 | `settings.json` 的 permissions（allow / deny / ask）与 hooks：PostToolUse（如 Edit/Write 后跑格式化）、PreToolUse（硬拦截）、Stop（退出前验证） |

其中最容易误解的是权限：`settings.json` 是 Harness 强制执行的配置，不是模型“建议遵守”的散文；deny 在任一层出现即全局生效；但 deny 只匹配命令文本——拦 `rm` 拦不住 `find . -delete`，硬拦截要靠 PreToolUse 钩子。同样，CLAUDE.md 里写“必须用 pnpm”可能被遗忘，PreToolUse 钩子拦 `npm install` 则每次都生效。**一句话：散文管建议，配置与钩子管保证。**

还有一个审计提醒：会话轨迹文件若就在 Agent 自己的文件权限范围内，Agent 理论上能改写记录自己行为的文件。审计不能只依赖“我读一下它的轨迹”，轨迹本身的完整性也需要 Harness 之外的保障。

## 七、评测 Harness：不要只看通过率，要看“差分、单次与成本”

评测 Harness 包住 Agent 打分，运行 Harness 包住模型干活，两者混用是看榜单时最常见的错误。

### 1. 目标状态差分（goal-state diff）比“输出像不像”更可信

LLM Book 第 43.2 节的要点：一次 Agent 运行是一条轨迹，有状态、有副作用、有多条正确路径。只比聊天输出，会漏掉“话说对了、事没办成”和“话说得不一样、事办成了”两种情况。最有用的评分原语是**目标状态差分**：跑完之后，世界的状态（文件、数据库、测试结果）与目标状态差多少。SWE-bench 的硬标准就是这一思想的实例：原来失败的测试必须全过，原来通过的测试一个都不能破，外加 Docker 隔离、超时与日志。

部分成功也要保留信号：用步骤相似度或子任务加权，而不是全对才算分；τ-bench 的双控提醒我们，真实任务里用户也会同时改状态，评测要能区分“Agent 的改动”与“环境的改动”。

### 2. pass@1 与 pass@k 是两个问题，成本曲线是第三个问题

- **pass@k**（k 次里至少成功一次）容易误读：一个 10 次里成功 1 次的 Agent 也能有很高的 pass@10，但生产上你通常只会给它一次机会。
- **pass@1** 才是“一次就成”的生产指标；报 pass@k 时必须同时报 k、运行次数、中位数与波动。
- **成本曲线**是独立的一维：每任务平均 token 数、每任务平均花费、每解决一个任务的花费。同一模型换 Harness，分数可能持平、成本却差 3 倍——近期的对照研究正是指向这一点：成本主要来自每次调用都重发的系统提示词等固定开销，任务越长，复利越明显。

所以看任何榜单，至少要同时问四句：用的什么 Harness（及配置）？跑了几次、报的是 pass@1 还是 pass@k？每成功一次花多少钱？轨迹怎么样（调了多少次工具、有没有绕路、参数是否合法）？四句缺一句，结论都不可比。

## 八、可以直接抄的最小 Harness 检查清单

这是本报告的交付物：不搭大系统，先把下面 12 项做齐，再谈加部件。每项后面括号里是它对应的失败模式。

**循环与上限**
- [ ] 有显式 while 循环与停止条件：模型不再请求工具、达到最大轮数、token 上限、花费上限、耗时上限，任一触发即停（防开放任务烧穿预算）。
- [ ] 只读工具可并行，写文件、改代码、跑命令串行（防状态互相冲突）。
- [ ] 每次调用的请求结构固定：系统提示词 + 工具 schema + 对话历史 + 最新消息，且日志里能复现（排障先看“当时到底发了什么”）。

**工具与权限**
- [ ] 每个工具都有清晰的名字、自然语言描述、参数 schema；被拒绝的调用以明确的工具结果返回，让模型换路，而不是悄悄失败。
- [ ] 工具分三档：自动执行 / 需人确认 / 直接禁止；禁止规则写进 Harness 配置（如 settings.json 的 deny），而不是只写进提示词；文本匹配拦不住的危险操作，用 PreToolUse 类钩子硬拦。
- [ ] 大工具输出截断或落盘：只把开头结尾留在上下文，完整内容写磁盘按需再读（防一轮输出吃掉大半窗口）。

**上下文与记忆**
- [ ] 关键规则放在每次重注入的项目指令文件（如 CLAUDE.md / AGENTS.md），而不是只放在第一条用户消息（防压缩后丢失）。
- [ ] 跨会话记忆落盘：进度文件 + 功能清单 + git 提交；每会话开始先读进度、再选下一个未完成项；每会话结束必须落在“下一个会话一分钟能接上”的干净状态。

**验证与停止**
- [ ] 退出前验证是钩子，不是请求：Stop / verify-on-stop 护栏检查“改了代码是否有新验证证据”，不通过就不让退出，改写为继续执行。
- [ ] 完成标准是合同，不是感觉：每个任务块开始前先定“做什么、怎么验证通过”，做完按合同逐项核对；Web 应用要加浏览器端到端验证，不能只跑单元测试。
- [ ] 评测与运行分开记账：报结果时同时报 Harness 配置、pass@1、成本曲线、轨迹摘要；只报通过率的结论，一律视为不可比。

**编排（用到多 Agent 时才加）**
- [ ] 先定路线再写代码：专家直接对用户说话用 handoff，管理者保留最终答案用 agents as tools；handoff 的授权在 `onHandoff` 开头抛异常实现，历史过滤用 `inputFilter` 且承认“已抄进消息的敏感内容清不掉”。

## 九、给 Patrick 的实用启示

1. **选 Agent 先看 Harness，不只看模型名。** 问一句“它的循环、权限、验证和记忆是怎么做的”，比问“用的是哪个模型”更有用；换一份 settings.json + CLAUDE.md + 技能组合，就是换了一套外 Harness。
2. **从最小循环起步，不要一上来堆工具。** 先有带上限、带日志、只读可并行的最小循环，再按需加沙箱、进度文件、验证钩子；每加一个部件，先说出它对应哪种行为。
3. **把重复检查写成确定性规则。** “跑测试、检查清单、通过标准”由 Harness 强制执行，而不是只在提示词里写“请认真测试”。
4. **工具描述就是产品文档。** 描述写不清楚，模型就会用错；改了工具 schema，就要重新跑评测。
5. **长期任务的记忆要落盘。** 进度文件加 git 提交，比“希望模型记得上一轮”可靠得多。
6. **看评测要同时看四样：** Harness 配置、pass@1、成本曲线、轨迹。只看通过率，很容易为一个又贵又绕的 Agent 买单。
7. **模型升级时，重测你的 Harness。** 上一代模型必需的部件（如上下文重置、每 sprint 的 Evaluator），下一代可能已不再承重；留着它们就是在为过期假设付 token。

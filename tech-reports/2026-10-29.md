# 每日 AI 技术报告 · 2026-10-29

**日期：** 2026 年 10 月 29 日（星期四）
**今日技术主题一句话概括：** Harness 工程——模型本身不变，换一套围绕它的“外骨骼”，Agent 就从一个聊天窗口变成能长期干活、能被验证的系统。

> 说明：本报告基于 2026 年 10 月 29 日检索到的公开资料整理，包括 Anthropic 的长时 Agent 工程文章、Agent Harness 的概念梳理和 SWE-bench 的评测介绍。其中一些 2026 年的归因（例如某一项改进到底多大程度上来自 Harness）仍在争论，报告里会把已验证的机制和仍需存疑的说法分开，不要把个案当成普遍结论。

## 一、通俗理解：模型是脑，Harness 是身体和工作制度

一个基础大模型，本质上是一个无状态的函数：输入一串 token，输出下一串 token。它自己不会打开文件、不会跑测试、不会记得你上周说了什么，更不知道自己刚才那步到底做成了没有。

Harness 就是包在模型外面的全部软件基础设施。业内常用一个公式概括：

**Agent = Model + Harness**

换句话说：如果你不是模型本身，你就是 Harness。系统提示词、工具定义、沙箱、权限检查、上下文拼装、记忆文件、子 Agent 的派生、停止条件、验证钩子，全都属于 Harness。

这个区分之所以重要，是因为生产中的很多失败不是模型“不够聪明”，而是 Harness 没给它安排好：工具输出太乱、关键指令在上下文压缩后丢了、没有明确的完成标准、出错后没有恢复路径。换一个模型往往变化不大，改一下 Harness 的重试规则、上下文策略或停止条件，整个 Agent 的表现可能完全不同。

## 二、核心机制拆解

### 1. 执行循环：Agent 的心跳就是一个 while 循环

最常见的循环长这样，源自 ReAct 的“思考—行动—观察”模式，现在大多藏在结构化工具调用后面：

1. Harness 组装一次请求：系统提示词、工具 schema、对话历史、最新消息。
2. 调用模型。模型返回文本，或者一个或多个工具调用请求，或者两者都有。
3. 如果模型还在请求工具，Harness 先做权限检查和钩子处理，再真正执行工具，把结果以工具结果的形式拼回对话，回到第 1 步。
4. 如果模型不再请求工具，就停止。停止的原因可能是正常结束，也可能是达到 token 上限、触发停止序列或拒绝执行，Harness 要对每种情况分别处理。

两个容易被忽略的细节：

- **并行与串行要分开。** 只读工具（读文件、搜索、查目录）通常可以并行；写文件、改代码、跑命令这类会改变状态的操作，通常要串行，避免互相冲突。
- **循环一定要有上限。** 最大轮数、最大 token 数、最大花费、最大耗时，缺一个都可能让一个卡住的 Agent 在“改进这个代码库”这种开放任务里一直烧钱。

### 2. 工具层：模型看到的工具描述，就是它理解的全部

模型自己不执行任何东西，它只发出结构化的工具调用请求，真正执行的是 Harness 的代码。所以工具定义的质量直接决定 Agent 的能力边界：

- 工具名、自然语言描述和参数 schema 要写清楚，因为模型只能靠这些文字判断什么时候该用、该传什么。
- 工具要分权限：哪些自动执行，哪些要人确认，哪些直接禁止。一个被拒绝的工具调用应该以明确的工具结果返回给模型，让它换一条路，而不是悄悄失败。
- 工具输出也是输入：一次返回 50KB 的报错或整份源文件，可能一轮就把上下文窗口吃掉大半。好的 Harness 会做截断、摘要或把完整内容写到磁盘上，让模型按需再读。

### 3. 上下文管理：Harness 每次调用前都在“拼提示词”

很多人以为上下文窗口里主要是对话历史，实际上消耗最大的常常是系统提示词、工具定义、项目指令文件和不断累积的工具输出。Harness 有三种常用手段：

- **压缩（Compaction）：** 窗口快满时，把较早的历史摘要化，保留最近的交流和关键决策。关键规则、构建命令这类“必须一直生效”的内容，应该放在每次都会重新注入的项目指令文件（例如 `CLAUDE.md` / `AGENTS.md`）里，而不是只放在第一条用户消息里，因为压缩后原始消息可能已经不在了。
- **工具输出外置：** 只把大输出的开头和结尾留在上下文里，完整内容落盘，需要时再读。
- **渐进披露：** 不要一开始就把所有工具的完整 schema 都塞进去，先给简短说明，模型真正需要时再加载完整定义。这能缓解“上下文越满，模型表现越差”的上下文腐化问题。

### 4. 记忆与状态要分层，不要只靠对话历史

Harness 里的“记忆”至少有四层：

1. **当前上下文窗口：** 短期、易失、昂贵。
2. **会话记录：** 一次运行的完整日志，用于恢复和分叉。
3. **项目指令文件：** 人写的长期规则，例如架构说明、构建命令、“改迁移前必须先确认”。
4. **Agent 自己写的状态文件：** 进度日志、待办清单、检查清单。这些文件和 git 历史一起，构成跨会话的记忆。

Anthropic 在长时 Agent 的实践里把这一点做得很具体：第一个会话先由一个初始化 Agent 准备环境，写好启动脚本、进度文件、初始 git 提交；之后的每个编码 Agent 会话只做一件事：读进度、选一个还没通过的功能、实现它、自己验证、提交并更新进度。功能清单里每个功能一开始都标记为未通过，Agent 只能改那个通过状态，不能删测试、不能把没做完说成做完了。

这个设计针对的是两个真实失败模式：一是一次性想把整个应用做完，做到一半上下文用完，留下一个半成品；二是后面的会话看到已经有进展，就直接宣布大功告成。一份“倔强”的功能清单加 git 提交，就是 Harness 层面的解法，而不是靠提示词多说一句“请认真一点”。

### 5. 子 Agent：隔离上下文，而不是单纯分工

任务一大，Harness 常常派生子 Agent，常见的两种模式要分清：

- **Agents as tools：** 主 Agent 保留最终回复权，把一个有边界的子任务交给 specialist， specialist 只返回简短结果，主 Agent 再综合。适合需要统一流程和统一护栏的场景。
- **Handoff（交接）：** 分诊 Agent 把整个对话交给 specialist， specialist 此后直接对用户负责。适合 specialist 应该直接说话、且有自己指令和工具的场景。

更关键的是上下文收益：子 Agent 通常用全新的对话开始，只把最终摘要（几百到几千 token）还给主 Agent，而不是把全部探索过程都塞回去。所以子 Agent 首先是一种上下文管理手段，其次才是一种组织方式。

### 6. 停止条件和验证：确定性检查比“请你认真检查”更可靠

Harness 可以在循环的关键点挂钩子，这些钩子在模型上下文之外运行，不烧 token，例如：

- 工具执行前拦截危险命令；
- 工具执行后做 lint 或测试；
- Agent 想退出时，先检查测试是否真的通过，不通过就不让它退出（这就是常说的 Ralph Loop：拦住退出尝试，把原始目标重新注入一个干净的上下文，再按完成标准跑一遍，中间状态存在文件系统里）。

对 Web 应用，Anthropic 的经验是：只跑单元测试不够，必须像真人用户那样用浏览器走一遍端到端流程，才能发现很多光看代码发现不了的 bug。验证方式本身也是 Harness 的一部分。

## 三、容易混淆的第二种 Harness：评测 Harness

“Harness”这个词还有另一个常见用法：评测 Harness。它不负责让 Agent 干活，而是负责给 Agent 打分。两者要分开看，不然看榜单很容易被误导。

以 SWE-bench 为例：每个任务给 Agent 一个真实 GitHub issue 和出问题那一刻的代码快照，Agent 要自己读代码、改代码、产出一个补丁。评分标准是硬性的：原来失败的测试必须全部通过，原来通过的测试一个都不能被破坏。整个过程通常在 Docker 隔离环境里跑，超时、日志、通过率都要记录。

评测 Harness 带来的几个提醒：

- **同一模型换 Harness，分数可能大变。** 评分测的是“模型 + Harness”这个整体，不是裸模型。
- **单次通过率不够。** Agent 运行本身有随机性，工具延迟和状态顺序都会影响结果。更可信的做法是多次运行，看 pass@N（N 次里至少成功一次的概率），同时报告中位数和波动。
- **只看最终答案不够。** 还要看轨迹质量：调了多少次工具、有没有浪费探索、有没有调对工具、参数是否合法。只看结果对不对，会漏掉很多系统性短板。
- **成本也要一起看。** 通过率之外，每任务平均 token 数、每任务平均花费、每解决一个任务的花费，都是选型时真正会付的账。

## 四、内 Harness 与外 Harness

Thoughtworks 的区分也值得记住：

- **内 Harness：** 模型厂商自带的，例如 Agent SDK、Claude Code、Codex 这类编码工具本身。
- **外 Harness：** 用户自己在上面搭的，例如项目指令文件、MCP 服务器、自定义技能。

再往下分，还有“引导”和“传感器”：引导是在行动前影响 Agent，例如指令和规则；传感器是在行动后观察结果并让 Agent 自我纠正，例如 lint、测试这类确定性检查，或者“用另一个模型当评委”这类推断性检查。好的系统通常是两者混用，而不是只靠其中一种。

## 五、给 Patrick 的实用启示

1. **选 Agent 先看 Harness，不只看模型名。** 同一个模型，放在不同的 Harness 里，长期任务的表现可能差很多。问一句“它的循环、权限、验证和记忆是怎么做的”，比问“用的是哪个模型”更有用。
2. **从最小循环起步，不要一上来就堆工具。** 先有一个带上限、带日志、只读工具可并行的最小循环，再按需加沙箱、进度文件和验证钩子。
3. **把重复检查写成确定性规则。** “跑测试、检查清单、通过标准”应该由 Harness 强制执行，而不是只在提示词里写“请认真测试”。
4. **工具描述就是产品文档。** 工具名和描述写不清楚，模型就会用错；改了工具 schema，就要重新跑评测，因为模型可能是在旧 schema 上训练出来的。
5. **长期任务的记忆要落盘。** 进度文件加 git 提交，比“希望模型记得上一轮”可靠得多。每次会话开始先读进度、再选下一个未完成项，是一个可以直接抄的模式。
6. **看评测要同时看三样东西：** 通过率、成本、轨迹。只看通过率，很容易为一个又贵又绕的 Agent 买单。

## 六、可以动手试的小练习

不用先搭大系统，先做一个最小实验：写一个只有读文件、列目录、跑测试三个工具的循环，给它设好最大轮数和花费上限，再给它一个“把进度写进一个 progress 文件”的规则。跑两次，对比一下：有进度文件和没有进度文件，第二次会话恢复任务的速度差多少；再试一次把“退出前必须测试通过”写成钩子，看它还会不会提前宣布完成。这个练习本身不大，但能直接摸到 Harness 的三个核心：循环、记忆、验证。

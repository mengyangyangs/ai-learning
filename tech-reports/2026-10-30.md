# 每日 AI 技术报告 · 2026-10-30

**日期：** 2026 年 10 月 30 日（星期五）
**今日技术主题一句话概括：** 推理优化不是“换个更快的模型”，而是把一次生成拆成算力、显存带宽与数据搬运三笔账，再用缓存、批处理、量化、推测解码与引擎选型分别去省。

> 说明：本报告基于 2026 年 10 月 30 日通过浏览器阅读的公开资料写成，包括推理优化指南、vLLM / SGLang / TensorRT-LLM 对比、推测解码分析、GPTQ 与 AWQ 对比、Prefill/Decode 解耦教材章节与 FlashAttention、PagedAttention 的讲解。文中凡是厂商或单篇基准的数字，均已标注为“某来源的测量”，不是通用结论；凡是教材里的模拟数字，均已说明是带假设参数的模型推演，不是生产实测。

## 一、通俗解释：为什么“生成一个字”这么贵

想象模型是一座图书馆：权重是全部藏书，KV 缓存是你正在读的那本书的书签与笔记。

- **Prefill（预填充）：** 你把整段提示词一次性交给模型，它并行算一遍，产出第一个 token，同时把每个 token 的 Key 与 Value 存下来。这一步算力密集，像“开馆时把整批新书一次编目”，决定了**首 token 延迟（TTFT）**。
- **Decode（解码）：** 之后每生成一个 token，模型只算这一个新位置，但要把之前所有 token 的 Key、Value 连同全部权重从显存里再读一遍。这一步不是算不动，而是**搬不动**：每步的算术量很小，瓶颈是显存带宽，决定了**每 token 时间（TPOT）**与流畅感。

所以优化推理，本质是回答三个问题：能不能少搬运？能不能一次搬运服务更多请求？能不能把搬运的东西变小？后面所有技术，都是这三个问题的不同答案。

衡量时先分清四个指标，别只看“每秒多少 token”：

| 指标 | 含义 | 2026 年指南里常见的健康目标（仅作参考） |
|---|---|---|
| TTFT | 从发请求到第一个 token 流出 | 聊天场景 4K 内提示词争取 < 500 ms |
| TPOT / ITL | 相邻 token 的间隔 | 7B–70B 在 H100 上约 30–60 ms |
| 总吞吐 | 一台服务器所有请求 token / 秒 | 单台 8×H100 + vLLM 约 5K–20K t/s（视模型与负载而定） |
| Goodput | 在满足 SLO 的前提下的有效吞吐 | 容量规划真正该看的北极星：总吞吐高、但 p95 TTFT 爆掉，等于没达标 |

## 二、关键机制一：KV 缓存——先算清它有多大，再谈怎么省

KV 缓存的大小可以用一个公式估算（每 token、每层、每请求）：

```
KV 字节 ≈ 2（K 与 V）× 层数 × KV 头数 × 头维度 × 序列长度 × 批大小 × 每值字节数
```

它随序列长度与并发数线性增长，长上下文与高并发一上来，权重反而不再是唯一的大头。举两个当天读到的具体例子：

- Liquid LFM3-1.7B 在 128K 上下文下 KV 缓存只要 1.6GB，而对比的 Qwen3.5-4B 要 4.3GB、MiniCPM5-2B 要 5.6GB——这是架构（卷积 + 滑动窗口注意力占比高）把“每 token 要存多少”本身压小了。
- Spheron 的 H100 对比里提到，70B 模型用 FP8 时权重本身已约占 70GB，80GB 的 H100 剩给 KV 缓存的空间很窄，稍不注意就要调小 `max-model-len` 或 `max-num-seqs`，否则会在请求中途 OOM。

省 KV 缓存有三条不同路线的技术，别混为一谈：

### 1. PagedAttention：像操作系统分页一样管显存

vLLM 的 PagedAttention（Kwon 等，SOSP 2023）把 KV 缓存切成固定大小的块（vLLM 默认每块 16 个 token），按需从空闲池里取，不再为每个请求预先划一整块“按最大长度算”的连续显存；每个请求用一张块表记录逻辑块到物理块的映射，注意力核按表取数。

它解决的是**碎片**，不是“总量”：旧系统因预留连续空间浪费 60–80% 的 KV 显存，vLLM 测量里浪费被压到最后一块未填满的部分（< 4%），缓存利用率从 Orca 类系统的 20–38% 提到 96.3%（教材引用的论文测量）。并行采样、Beam Search 这类“多个序列共享前缀”的场景还能共享物理块，论文称可省多达 55% 的内存、带来最高 2.2 倍吞吐。

代价也要说清：注意力核必须改写以支持分页，框架要自己实现一套内存管理器。后续的 vAttention 论文正是针对这一点：用操作系统已有的按需分页保留虚拟连续性，让未改写的注意力核也能动态分配，作者称在 vLLM 栈里解码吞吐最高比 vLLM 快 1.99 倍——但这是该论文自己的测量，不是 vLLM 官方结论。

### 2. RadixAttention 与前缀缓存：别重复算已经算过的提示词

SGLang 的 RadixAttention 把缓存块组织成一棵按 token 序列索引的基数树（radix tree）：两个请求共享一段前缀（系统提示词、Few-shot 示例、RAG 文档），就只算一次、后面复用。vLLM 也有自动前缀缓存，但 SGLang 把“跨请求共享”做成了核心机制。

效果取决于你的流量里“有多少是重复的”：

- 前缀密集型流量、50 并发时，Spheron 的测量称 SGLang 比 vLLM 的 TTFT p50 低 37%、p95 低 41%；
- 提示词各不相同时，优势缩到约 3.8%，基本在基准噪声内；Runpod 的另一组对比也呈现同一规律（前缀密集约 +29%，无共享前缀时只差 1–4%）。

**一个极易踩的坑：** 前缀缓存要求前缀字节级相同。在系统提示词顶部插一个用户 ID、时间戳或会话 ID，就会把命中率直接打掉。Agent 场景里，工具定义、系统提示词越稳定，缓存收益越大；反之，动态拼接的提示词等于主动放弃这项优化。

### 3. 更少的 KV 头与更低精度的 KV：从模型结构与数值上省

- **MQA / GQA：** 多个 Query 头共享同一组 Key、Value 头，KV 量直接按共享倍数缩小。LFM3 的滑动窗口注意力也是同类思路：不是所有层都需要看全部历史。
- **KV 缓存量化：** 把 K、V 从 16-bit 压到 8-bit 甚至 3–4-bit，长上下文下收益尤其大；但与权重量化一样，必须在自己的任务上测精度回归，不能只看显存数字。

## 三、关键机制二：批处理与调度——让一次搬运服务更多人

### 连续批处理（Continuous Batching）

静态批处理要等整批请求都跑完才接新请求；连续批处理（源自 Orca，OSDI 2022）在每轮解码步结束时，把已完成的序列换出、把新请求换入，GPU 不用在“等最慢的那个”上空转。指南里常见的说法是：混合聊天负载下比静态批处理高 2–4 倍有效吞吐，某些生产总结称可达 10–20 倍——区间这么宽，恰恰说明它极度依赖负载形状，不能直接照搬。

### 分块 Prefill（Chunked Prefill）

长提示词的 Prefill 一次性会把 GPU 占住几十毫秒，正在解码的其他请求全部被迫等待，表现为 token 流“卡一下再续上”。分块 Prefill 把长 Prefill 切成小块，与解码步交错执行：既不让单个 Prefill 独占 GPU，也不让新请求无限排队。这是单机上最常用的折中方案。

### Prefill / Decode 解耦（Disaggregation）：给两个阶段各配一拨机器

DistServe（2024）、Splitwise（2024）、Mooncake（Kimi 背后的架构）把这个想法推到极致：Prefill 池只做 Prefill，Decode 池只做 Decode，中间只传 KV 缓存；vLLM、SGLang、TensorRT-LLM 现在都提供或文档化了这类模式（vLLM 里是 `kv_transfer_config` 的 producer / consumer 角色）。

教材《Scaling Out AI》第 24.5 节用一个带假设参数的离散事件模拟把利弊算得很清楚，**必须按模拟读，不能当生产基准**：

- 模拟设定：8 个长提示词突发到达，SLO 为 p99 TTFT ≤ 350 ms、p99 TPOT ≤ 20 ms，KV 传输固定 4 ms；
- 同机部署：p99 TTFT 1064 ms、p99 TPOT 292 ms，两项 SLO 全挂——最坏的解码步要等 140 ms 的 Prefill  burst，一次次叠加；
- 解耦部署：p99 TTFT 252 ms、p99 TPOT 8 ms，两项通过——代价只是每请求 +4 ms 的传输。

公式上就是：`TTFT = 排队 + Prefill + KV 传输`，`TPOT ≈ 每步成本 + 每步等待`。解耦加了常数项 `KV 传输`，但把原来尖峰式的“等待 Prefill”几乎清零。什么时候该用、什么时候不该用，教材的结论很干净：

| 场景 | 结论 |
|---|---|
| 高负载、长提示词、TPOT SLO 很紧 | 解耦赢：干扰成本远大于传输成本 |
| 轻负载 | 不赢：本来就没什么解码可被打断，传输纯属 overhead |
| 池间互联慢 | 可能输：传输不再是常数，开始主导 TTFT |
| 单机中等流量 | 先用分块 Prefill：简单，且往往够用 |

还有两个运维代价：两拨池子要按“提示词 token 到达量”与“输出 token 到达量”分别定容（不是按请求数），以及 Decode 副本挂掉时它手里的 KV 缓存怎么办，需要故障处理预案。

## 四、关键机制三：FlashAttention——不改数学，只改“数据住哪”

标准注意力要先算出 N×N 的分数矩阵 S = QKᵀ，写回 HBM，再读回来做 Softmax、再乘 V。N 一大，搬运本身就成了瓶颈。FlashAttention（Dao 等，2022）的核心是 **IO-aware（面向 IO 设计）**：不数 FLOPs，数“在 HBM 与 SRAM 之间搬了多少字节”。

- GPU 有两级存储：HBM 大（A100 约 40–80GB，约 1.5–2.0 TB/s）、SRAM 小（A100 每 SM 约 192KB，但约 19 TB/s）。标准注意力把中间矩阵反复写回 HBM，90% 以上的时间可能花在搬运上。
- FlashAttention 把 Q、K、V 切成能塞进 SRAM 的小块（tile），在片上算完分数、Softmax 与加权和，只把最终输出写回 HBM，内存从 O(N²) 降到 O(N)。
- Softmax 本来要看完整行才能归一化，解法是**在线 Softmax（online softmax）**：维护每行的 running max 与 running sum，新块进来时按新的 max 重缩放旧结果，再累加——结果与标准注意力在浮点舍入内一致，**是精确算法，不是近似**。

适用边界也要记：短序列、小批量时注意力本身的 HBM 流量不大， tiling 的额外开销可能反而拖慢；需要 FP32 精确注意力的研究场景也不宜直接套用。FlashAttention-4（2026，面向 Blackwell）据讲解文章称在 B200 上 BF16 可达约 1613 TFLOPs/s（约峰值的 71%），这是厂商侧的报告，引用时要保留这一限定。

## 五、关键机制四：量化——GPTQ 与 AWQ 解决的是同一个目标，手段正好相反

先统一记号：W4A16 表示权重 4-bit、激活 16-bit；W8A8、W4A4 以此类推。容器（safetensors、GGUF）与方法（GPTQ、AWQ）是两回事：同一个 INT4 文件，可能是两种算法算出来的。

共享问题是：把一层 `Y = WX` 的权重按组（默认 128 个输入通道一组）压到 16 个档位（4-bit），每组一个 scale、一个 zero point：

```
scale = (max - min) / 15
q = clamp(round(w / scale) + zero, 0, 15)
w_hat = scale × (q - zero)
```

直接按最近值取整（RTN）在 8-bit 时近乎无损，到 4-bit 常在推理与长文本上 visibly 变差，原因有二：每权重的误差会沿着真实输入累积；少数输入通道的激活远大于其他通道，其权重误差会被成倍放大。GPTQ 与 AWQ 都以“让 `||WX - ŴX||²` 在校准激活上最小”为目标，只是攻击点不同：

### GPTQ：把刚犯的错，推给还没量化的权重

源自 Optimal Brain Surgeon 思想（Frantar 等，ICLR 2023）：对一行的平方误差，二阶矩阵是 `H = 2XXᵀ`；把第 i 列量化后产生的误差，按 `H⁻¹` 的第 i 行成比例地修正尚未量化的列。工程上的关键是：对所有行用固定列顺序、一次 Cholesky 分解读 `H⁻¹`、按 128 列分块做矩阵乘，而不是逐列做秩一更新，从而把 175B 规模的计算变得可行。

- **Dampening：** 给 H 的对角加约 1% 的均值，防止校准集里从未激活的通道让矩阵不可逆。
- **Act-order（desc_act）：** 先量化 `diag(H)` 最大的列（即对输出影响最大的输入通道），此时还有最多未量化列可吸收误差；代价是检查点必须带 `g_idx`（每个输入通道属于哪一组）。
- **代价与风险：** 自由度大——拟合得好可以更贴近原模型，校准数据偏了也会把偏见拟合进去；大模型上 Hessian 本身就很占显存（讲解文章举例：70B 的 `down_proj` 输入宽 28,672，Hessian 约 3.3GB，需积极 offload）。

### AWQ：把重要的通道先放大，让取整对它更宽容

源自 MIT Song Han 组（Lin 等，MLSys 2024 最佳论文）：观察是，约 0.1–1% 的权重通道由**激活幅度**（而非权重幅度）决定，保护它们就能挽回 RTN 的大部分损失。AWQ 不用混合精度存这些通道，而是用一个精确恒等式：

```
WX = (W·diag(s)) · (diag(s)⁻¹X)
```

把显著通道的权重先乘 s 放大再取整，相对取整误差就变小；逆缩放 s⁻¹ 折进产生 X 的前一个算子（Llama 结构里：RMSNorm 吸收 q/k/v 的，MLP 前的 Norm 吸收 gate/up 的，`up_proj` 吸收 `down_proj` 的），推理时零额外成本。搜索的自由度只有一个指数 α（每组层一个）加每组的裁剪比，因此校准数据需求小、不易过拟合；Hugging Face 的经验估计称 8B 模型 AWQ 校准约 10 分钟、GPTQ 约 20 分钟（单张 A100），仅作量级参考。

两者在落盘后是一样的东西：`qweight`（每 int32 打包 8 个 4-bit 值）、`scales`、`qzeros`，GPTQ 开 act-order 时多一个 `g_idx`。8B 级模型按 4-bit + 每 128 权重一个 16-bit scale 与 4-bit zero 算，约 4.16 bit / 权重；讲解文章的 Llama-3-8B 形模型例子：线性层约 3.63GB，embedding 与 LM head 若保持 FP16 另占 2.10GB，整文件约 5.7GB（FP16 原版约 16.1GB）。

**选型结论（来自对比文章，不是口号）：** 在同一 Marlin 类内核上跑，两者的吞吐通常打平——速度由内核决定，不由“谁算出的整数”决定。所以选 GPTQ 还是 AWQ，应以**同一评估套件、同一校准集、自己任务上的精度**为准；两者也可以叠加（先 AWQ 缩放、再 GPTQ 取整，llm-compressor 有这类配方），但要当作第三个候选测，而不是默认更优。

**量化失败模式清单（直接抄自对比文章的总结，值得贴在墙上）：**

- 校准集与线上流量不匹配（英文散文校准的代码 / 多语言模型，在线上恰恰丢最多）；GPTQ 因自由度大更暴露。
- 校准 token 数少于最宽层的输入通道数，Hessian 秩亏，全靠 dampening 撑着。
- MoE 里极少被路由到的专家几乎拿不到校准 token，等于“盲量化”——要查每专家 token 数，对饥饿专家回退到 RTN 或更高精度。
- AWQ 的逆缩放无处可折：新架构若没有对应的前置算子，那一层的缩放会被静默跳过。
- 只做权重量化不够时：激活也要压到 INT8 / FP8，需要 SmoothQuant 或旋转类方法另行处理。

2026 年的硬件默认值也值得记一条：Hopper / Blackwell 上 FP8（权重与激活）已是新默认，约可翻倍吞吐；Ampere（A100）一代则对应 INT8 + SmoothQuant / AWQ；Mistral Large 4 这次同时放出的 NVFP4 检查点，就是“为 Blackwell 定制的 4-bit 浮点量化”这一趋势的实例。

## 六、关键机制五：推测解码——无损加速，但只在“猜得准、批量小”时成立

机制分两步：小 draft 模型先自回归地猜 K 个 token；大 target 模型用一次前向并行验证全部 K 个，接受的留下、第一个拒绝处用 target 自己的分布重采样、之后的全丢弃。Leviathan 等（Google，2022）与 Chen 等（DeepMind，2023）各自证明：这套拒绝采样**不改变 target 模型的输出分布**，是无损加速，不是近似。

期望收益可以用接受率 a 与草案长度 K 估算：每轮期望接受约 `(1 - a^(K+1)) / (1 - a)` 个 token。a = 0.9 时几乎全中；a = 0.5 时每轮只约 1.4 个，还没算跑 draft 模型的成本——这就是“低于约 50% 接受率就可能比不推测更慢”的来源。

关键数字（均需注明条件）：

- EAGLE-3 在 batch size 1、temperature 0 时报告对 Vicuna-13B、Llama-3.1-8B、Llama-3.3-70B 有 4.1–6.5 倍加速；但同一 EAGLE 算法在 Llama-3-70B 上，batch 从 1 涨到 128 时加速从 1.96 倍塌到约 1.21 倍（arXiv:2508.08192 的测量）。
- 原因不是 draft 变差了，而是 GPU 的瓶颈变了：低并发时解码受显存带宽限制，验证多 token 几乎是“搭便车”；高并发时 GPU 本身已算满，验证只是额外算力。经验分界约在 batch 32 附近，超过后收益快速收敛。
- EAGLE 与 Medusa 的区别：Medusa 在 target 上加预测头、省去独立小模型；EAGLE 用 target 自身的隐藏状态训 draft，接受率更高；EAGLE-2 再引入“按上下文动态调整的 draft 树”，称比 EAGLE-1 快 20–40%。
- 选 draft 的起点法则：target 与 draft 参数比约 10–20 倍（如 70B 配 3–8B），同系列配对在常见聊天数据上接受率约 75–85%——但这只是先验，**必须在自己的流量上实测接受率**，代码补全上 80% 的 draft 换到别的领域可能跌破 50%。

还有两个长期代价常被忽略：一是 draft 与 target 的绑定——换 target 检查点往往要重训 / 重调 draft，这是“维护税”，不是一次性成本；二是长上下文的例外：MagicDec（arXiv:2408.11049）指出，上下文足够长、大批量时瓶颈会回到 KV 缓存带宽，推测解码的优势可能重新出现。因此未来的方向是**按请求动态开关**（如 D-cut 的自适应验证深度），而不是全局一个开关管到底。

Mistral Large 4 内置的 DSpark 推测解码头（一次提 3 个 token，官方称最高提速 1.9 倍）正是把 draft 做进模型本身的例子：省去了“另训一个小模型”的维护，但也把加速与该检查点绑定得更紧。

## 七、引擎选型：vLLM、SGLang、TensorRT-LLM 不是“谁最快”，而是“谁最配你的流量”

以下数字来自 Spheron 自有 H100 基准（Llama 3.3 70B FP8，50 并发，独特提示词），引用时必须保留这一限定，不能当作跨厂商结论：

| 引擎 | 吞吐（50 并发） | TTFT p50 | 冷启动到首请求 |
|---|---|---|---|
| vLLM | 1,850 tok/s | 380 ms | 约 62 秒 |
| TensorRT-LLM | 2,100 tok/s | 340 ms | 约 28 分钟（编译） |
| SGLang | 1,920 tok/s | 360 ms | 约 58 秒 |

同一基准的并发曲线也说明了取舍：vLLM 从 1 并发 120 tok/s 涨到 100 并发 2,400 tok/s（批量带来的 20 倍），但 TTFT p50 从 45 ms 涨到 740 ms——**批量买吞吐，是用单人延迟换的**。

决策表（按流量形状，而非榜单）：

| 你的情况 | 首选思路 |
|---|---|
| 提示词多样、模型换得勤、硬件不止 NVIDIA | vLLM：模型覆盖最广、多硬件、免编译 |
| 单一模型长期生产、每 token / 秒就是钱 | TensorRT-LLM：编译成针对 GPU / 批量 / 序列长度的核图，吞吐最高，但要付编译与 NVIDIA 锁定成本 |
| 系统提示词 / RAG 上下文 / 多轮 Agent 占大头（前缀重叠约 60% 以上） | SGLang：RadixAttention 的前缀复用直接省 Prefill |
| 混合流量 | 混用 + 路由：批量 / 后台走 vLLM 或 TensorRT-LLM，交互 / 前缀密集走 SGLang，按请求形状分流 |

量化的优化顺序（综合多篇指南的共识，按 ROI 排）：**先量化（FP8 / AWQ，省显存、换更便宜的卡）→ 再选引擎（按流量形状）→ 再按需加推测解码（只用于低并发、延迟敏感路径）→ 全程用 Prometheus / 轨迹监控（TTFT、TPOT、队列、显存、质量评估要成对看）**。

## 八、可以直接用的检查清单：上任何一项优化前，先过这 8 问

- [ ] **基线先行：** 是否已在真实流量分布上测过 TTFT、TPOT、吞吐、显存与任务精度？没有基线，任何“提速 X 倍”都无法归因。
- [ ] **瓶颈定性：** 当前是 Prefill 瓶颈（TTFT 高）还是 Decode 瓶颈（TPOT 高）？前者先看分块 Prefill / 解耦 / 前缀缓存，后者先看批量、KV 压缩与推测解码。
- [ ] **前缀是否稳定：** 系统提示词与工具定义是否字节级固定？有没有时间戳、用户 ID 混进前缀导致缓存失效？
- [ ] **量化评估是否成对：** 换精度后是否在 held-out 任务集（而非校准集）上重测了精度与 KL 散度？校准集是否覆盖线上语言与任务？
- [ ] **推测解码三数是否实测：** 自己流量上的接受率、典型批量、draft / target 参数比——三者是否同时落在收益区？
- [ ] **批量是否在收益区：** 批量 > 32 后推测解码是否还值得？批量上去后 TTFT p95 是否已超 SLO？
- [ ] **好 throughput 还是 goodput：** 总吞吐好看时，p95 TTFT / TPOT 是否仍在 SLO 内？队列深度是否在涨？
- [ ] **MoE 与新架构是否特判：** 饥饿专家、AWQ 折叠目标缺失、激活异常值这三类失败，是否已逐项排查？

## 九、给 Patrick 的实用启示

1. **个人使用不需要自建 70B 服务。** 想体验量化，直接用 llama.cpp / Ollama 的 GGUF 4-bit 本地模型：同一台机器上，4-bit 往往是“能不能跑起来”的分界线，而不是“快一点”的微调。
2. **写 Agent 提示词时，把“稳定前缀”当作性能设计。** 系统提示词、工具定义尽量固定、放前面；把每次都变的会话 ID、时间戳往后放——这能让服务端的 prefix caching 真正命中，TTFT 与成本都会受益。
3. **选 API 时别只比“模型名”，比“每成功任务的成本”。** 同一模型在不同服务商处，因引擎、量化与缓存策略不同，TTFT、TPOT 与价格可能差几倍；长上下文任务先算 KV 与 token 账单，再看榜单。
4. **不要把推测解码当万能开关。** 它最适合低并发的聊天与代码补全；批量任务、离线批处理里，它的收益会自然缩水，强行开启可能更慢。
5. **把今天的技术报告与昨天的 Harness 报告连起来读：** Harness 决定“Agent 干什么、怎么验证”，推理优化决定“同样的 Agent 跑起来花多少钱、多快”。两者叠加，才是 Agent 从“能跑 demo”到“能长期跑”的完整账本。

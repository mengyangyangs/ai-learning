# 每日 AI 技术报告 · 2026-10-31

**日期：** 2026 年 10 月 31 日（星期六）
**今日技术主题一句话概括：** RAG 答错，大多不是模型“想错了”，而是检索“没找对”——这份报告把一次问答拆成“找得到、排得准、答得住”三关，讲清楚分块、混合检索、重排与评测各自在修哪一关，以及各自会在哪里翻车。

> 说明：本报告基于 2026 年 10 月 31 日通过浏览器阅读的公开资料写成，包括 RAG 架构深挖、混合检索与重排讲解、Anthropic 上下文检索及其 2026 年反驳研究、查询改写家族与 AWS Bedrock 成本手册的相关章节。文中凡是单篇论文、单家厂商或单次测量的数字，均已标注来源与条件，不是通用结论；凡是“某来源的建议”，均已说明适用边界。

## 一、通俗解释：RAG 不是“让模型变聪明”，而是“考试开卷，但卷子要自己找”

想象你要回答一个关于公司政策的问题，面前是一座图书馆：

- **没有 RAG：** 你只能凭记忆回答。记忆可能是对的，也可能是三年前的旧版本，还可能把两家公司的政策拼在一起。
- **有 RAG：** 你先去图书馆找几页最相关的纸，把它们摊在桌上，再照着纸回答。答错的责任于是分成了两部分：纸找错了，还是照着纸还答错了？

RAG 的标准流程只有三步，但每一步都有自己的失败方式：

1. **入库（Ingestion）：** 把文档切成块（chunk），给每块算一个向量（embedding），连同关键词索引一起存起来；
2. **检索（Retrieval）：** 把用户问题也变成向量，找出最像的块，必要时再重排；
3. **生成（Generation）：** 把找来的块交给大模型，让它“只根据这些块”回答，并标出引用。

今天的报告只聚焦一个判断：**先修检索，再谈提示词。** 如果正确答案所在的块根本没进前 10 名，提示词写得再漂亮，模型也只能在错误或不完整的材料上“自信地编”。昨天的推理优化报告讲的是“同样的 Agent 跑起来花多少钱、多快”；今天讲的是“Agent 凭什么相信它拿到的资料”。

## 二、第一关：分块——切错了，后面全错

分块是 RAG 里最容易被低估的一步。一篇 2025 年的生产故障分析（被多篇 2026 年讲解引用）称，超过 80% 的生产 RAG 错误源自切块与索引阶段，而不是模型幻觉。这个数字是单篇分析的结论，不能当作普适比例，但它指对了方向：切块错了，检索无从谈起。

### 1. 固定长度切块：最快，也最脆

教程默认值常常是“每 512 token 一块，重叠 64 token”。它的问题不是“512”这个数，而是“在任意位置下刀”：

- 法律文件会在条款中间被切断；
- 代码会在函数中间被切断；
- 操作步骤会在“第 3 步”与“第 4 步”之间被切断。

重叠并不能修复断口，它只是把断口复制了两份。固定切块只适合一种语料：短小、同质的段落，如 FAQ、产品描述、客服记录。其他地方把它当默认，等于主动制造检索噪声。

### 2. 按结构切块：先按文档自己的骨架下刀

更好的起点是按文档结构切：标题、段落、列表项、表格行各自成块，表格不要拦腰切断。并且给每块加上“标题路径”前缀，例如：

```
计费 > 退款 > 部分退款
```

这样一块只写“需要 5 天”的内容，检索时仍然知道“这 5 天”说的是哪件事。2026 年的一份对照研究还给出一个更直接的结论：在稠密（向量）检索下，**按标题对齐切块的效果，优于给每块加一段 LLM 生成的上下文**（见第四节的争议）。也就是说，很多时候“切得对”比“补得巧”更有效。

### 3. 层级切块：小块用来找，大块用来答

层级切块解决了一个根本矛盾：检索要“准”（小块定位更精确），生成要“全”（大块上下文更完整）。

做法是把同一份文档切成两层甚至三层：

- 子块约 128–200 token：只对子块做向量索引，检索时用它定位；
- 父块约 512–1024 token：子块命中后，把整段父块交给模型。

LlamaIndex 的 `HierarchicalNodeParser` 与 `AutoMergingRetriever` 就是这套模式的现成实现（示例层级常为 1024 / 512 / 128 token）。代价是入库更复杂、索引更大；收益是“针尖定位 + 段落理解”可以兼得。

### 4. 语义切块：按话题边界切，不是按字数切

语义切块先把句子向量化，再把相似度高的句子归为一组，相似度骤降处断开。适合长篇散文、论文、混合主题报告；不适合对话记录这类话题跳跃快的语料。它的成本在入库时（要先算句子向量、再定阈值），阈值选得不好，反而会把不该合的合在一起。

**一个反直觉的提醒：** 2026 年 1 月的一项系统分析发现，在使用 SPLADE 这类稀疏检索时，切块重叠没有带来可测量的收益。重叠不是免费的：它增大索引、拖慢入库，却未必提高召回。不要把“重叠 10%–20%”当作不证自明的默认值，先在自己的数据上测。

## 三、第二关：检索——关键词与向量各瞎一只眼，合起来才看得全

### 1. 向量检索（Dense）：懂意思，认不出编号

向量检索把问题与文档块都变成向量，找余弦相似度最高的块。它擅长“意思相近但用词不同”，例如用户问“远程办公规定”，文档写的是“分布式 workforce 政策”。

它的盲区恰恰相反：**精确字符串**。问“错误码 E1042”“SKU 88-210”“某人姓氏”时，向量检索常常返回“主题相近但编号不对”的块。法律、金融、技术文档里，编号与专有名词恰恰是答案的钥匙。

### 2. BM25：认编号，不懂同义词

BM25 是搜索引擎用了几十年的关键词排序算法：词频越高、词越罕见，得分越高；同时对文档长度做归一化，避免长文档占便宜。它在 CPU 上就能跑，不需要 GPU、不需要向量索引，对没见过的新领域术语尤其稳健（BEIR 基准的经典结论：很多在领域内表现出色的稠密检索器，换到陌生领域反而不如 BM25 稳）。

它的盲区是镜像的：用户说“远程办公”，文档只写“分布式 workforce”，BM25 一个词都对不上。

### 3. 混合检索 + RRF：两路各跑各的，只比名次不比分数

生产标准做法是两路并行：BM25 取前 50、向量取前 50，再用**倒数排名融合（Reciprocal Rank Fusion, RRF）**合并：

```
score(d) = Σ 1 / (k + rank)
```

其中 `k` 常用 60（来自 RRF 原论文的默认值），`rank` 是该文档在某一路里的名次。只用名次、不用原始分数，是因为 BM25 分数与余弦相似度根本不在同一个量纲上，没法直接相加。

一篇 2026 年关于文本与表格文档的论文给出的对照（需注明：这是该论文在特定语料上的测量，不是通用保证）：

| 方法 | Recall@5 |
|---|---|
| 仅 BM25 | 0.644 |
| 仅向量 | 0.587 |
| 混合 RRF | 0.695 |
| 混合 RRF + 神经重排 | 0.816 |

规律比数字本身更重要：混合检索的提升是“稳定但有限”的，大头提升来自下一步的重排；而重排的代价是延迟（该文给出的本地量级：向量约 5ms、混合约 15–25ms、加排序后约 80–150ms，均为 p50 参考）。

### 4. 查询改写：问题本身写得不好，检索再强也没用

还有一类失败发生在检索之前：用户的问题根本不是好的查询。查询改写家族就是针对这四种“问法与答案长得不像”的情况：

| 不匹配类型 | 例子 | 修复思路 |
|---|---|---|
| 词汇鸿沟 | “能在西班牙远程工作一个月吗？”→ 文档写“跨境临时远程工作需事先审批” | HyDE：先让模型写一段“假设答案”，用它的向量去检索 |
| 抽象层次 | “2019 年的笔记本该换了吗？”→ 文档写“设备四年一换” | Step-back：先问更一般的问题，再回落到具体问题 |
| 复合问题 | “12 人团队，A 方案与 B 方案哪个便宜？” | 分解：拆成定价页 + 座位数规则，分别检索再合并 |
| 表述分散 | “为什么周一构建总失败？”→ 答案散在措辞各异的事故记录里 | 多查询：生成多个改写，并行检索后去重合并 |

但改写不是免费午餐，三个坑必须先说：

- **漂移：** 改写后的问题可能已经不是用户的问题。保险做法是始终保留原始查询，并检查引用是否与用户原话相关，而不是只与改写相关；
- **幻觉锚点：** HyDE 生成的假设答案可能编造一个不存在的编号、日期或人名，反而把检索带偏。做法是禁止改写里出现具体编号，并保持假设简短；
- **冗余与成本：** 多查询会产生 3–5 倍检索调用，HyDE 还要多一次模型调用；如果问题本身已经包含错误码、SKU 或政策编号——它已经是极好的查询，改写只会添乱。**好的进阶 RAG 系统先做“要不要改写”的判断，而不是把所有技巧全堆上去。**

## 四、一个值得认真对待的争议：上下文前缀到底有没有用？

Anthropic 2024 年提出的**上下文检索（Contextual Retrieval）**思路很直观：切块会让块“忘记自己来自哪篇文档”，例如一块只写“公司营收增长了 3%”，却丢了公司、季度与年份。解决办法是：对每块，用模型结合整篇文档写一段 50–100 token 的上下文，贴在块前面，再同时做向量索引（上下文嵌入）与关键词索引（上下文 BM25）。

Anthropic 当时的测量（代码库、小说、arXiv 与科学论文语料，top-20 失败率，即相关块未进前 20 的比例）：

| 方法 | top-20 失败率 | 相对降幅 |
|---|---|---|
| 基线 | 5.7% | — |
| 上下文嵌入 | 3.7% | 约 35% |
| 上下文嵌入 + 上下文 BM25 | 2.9% | 约 49% |
| 再加排序 | 1.9% | 约 67% |

成本上，Anthropic 称借助提示词缓存（同一文档只付一次），每百万文档 token 的上下文生成成本约 1.02 美元（按当时 800 token 块、8K 文档的示例算）。一篇 2026 年的复现测算提醒：按当时 Haiku 5.5 的标价重算，同一形状约 0.38 美元/百万 token，且 Anthropic 配套 notebook 自身的缓存命中率（61.83%）低于其正文暗示的 70%–80%——成本数字同样要以自己的账单为准，不能照搬。

但 2026 年的研究提出了反驳，值得原样记录而不是只引用 2024 年的 headline：

- 一项日语生产语料对照（150 篇博客文章、295 个改写问题 + 150 个词汇相近问题）发现：**稠密检索下，标题对齐切块优于上下文前缀**（nDCG@10 高出 0.070，统计显著）；BM25 下上下文仍有帮助（+0.030）；但混合检索 + 排序后，**各变体之间的差异基本消失**；
- 该研究的生产部署结果是：块级混合检索 + 排序，把“证据到达生成器的比例”从 59% 提到 81%，答案准确率从 67% 提到 87%，同时上下文从约 30,000 字符压到约 4,000 字符，代价是约 1.2 秒额外延迟。

**结论不是“上下文检索错了”，而是“不要把它当作必选项”：** 如果你的文档标题结构清晰，先做标题对齐切块；如果文档是“一段段没有标题的散文”，上下文前缀的收益更大；无论哪种，最终都要在自己的测试集上做 A/B，而不是照搬 49% 或 67% 这类 headline 数字。

## 五、第三关：重排与生成——把“找得到”变成“答得住”

### 1. 重排：先广撒网，再精挑细选

向量检索用的是“双编码器”：问题向量与块向量各自独立算好，再比相似度，速度快但判断粗。重排用的是“交叉编码器”：把“问题 + 候选块”成对喂给模型，让模型通读两者再打分，判断细得多，但贵得多——所以不能对全库用，只能对前 50 名用。

标准漏斗是：**混合检索取前 50 → 交叉编码器重排 → 留前 5–10 名交给模型**。常用开源选择是 BAAI 的 `bge-reranker-v2-m3`；该文给出的本地量级是 CPU 上每对约 8ms、50 对约 400ms，GPU 上整批可压到 50ms 以内。

重排的三个实操坑：

- **截断：** 交叉编码器常有 512 token 的输入上限（问题 + 块合计），块太长会被截断，答案恰好在被截掉的那半段里——块大小要按重排器来定，不只按嵌入模型来定；
- **语言不匹配：** 只支持英文的重排器用在中文或混合语言语料上，可能比不排序更差，要按语言分别测；
- **延迟线性增长：** 候选数翻倍，重排时间基本翻倍。先测“候选数到多少时召回不再增长”，再定候选数，不要拍脑袋定 100。

### 2. 生成侧：引用、拒绝与“找不到就说找不到”

检索做对了，生成侧还有三件事：

- **引用要落到块：** 答案里的每个关键事实都应能对应到某个被检索到的块；引用编号不能是模型“编出来的块号”，要来自检索结果的真实 ID；
- **没找到要明说：** 如果重排后的最高分低于你在测试集上标定的阈值，正确回答是“我在这份文档里没找到”，而不是把几个 loosely 相关的块拼成一个自信的答案；
- **块利用率：** 检索到的块如果从未进入最终答案，说明要么检索太宽、要么生成在忽略证据——这两个问题要分开修。

### 3. 权限与隔离：过滤必须发生在排序之前

这是今天最容易被提示词掩盖的一点，也是与资讯报告里 Cloudflare 事件直接呼应的地方：

- 租户、年份、产品、用户权限这类过滤条件，必须作为元数据过滤在**检索之前**、在向量库索引层执行，而不是事后靠提示词说“不要提机密文档”——提示词不是访问控制；
- 两路检索要**同时**过滤：如果只对向量路过滤、不对 BM25 路过滤，融合步骤会把本不该出现的东西重新带回来；
- 共享推理基础设施的隔离同样重要：Cloudflare 事件里，超长请求的旧缓存页被错误复用，说明“缓存复用”与“租户隔离”必须一起设计，而不是只优化命中率。

## 六、评测：没有测试集的 RAG，都是“感觉良好”

RAG 的评测要分阶段测，不能只看最终答案好不好看：

| 阶段 | 指标 | 它抓什么问题 |
|---|---|---|
| 检索 | recall@k | 答案所在的块有没有进前 k 名（k=5 时 recall 60% 意味着 4 成问题在生成前就已丢答案） |
| 检索 | MRR / nDCG | 正确答案排在第 1 名还是第 9 名；排序质量是否在提升 |
| 检索 | Context Precision / Context Recall | 找来的块对不对、找全了没有 |
| 生成 | Faithfulness（忠实度） | 答案是否超出了检索到的内容（幻觉） |
| 生成 | Citation Correctness（引用正确性） | 引用是否真实对应到块 |
| 系统 | TTFT、每请求成本、块利用率 | 延迟与成本是否随检索步骤失控 |

实操建议（来自多篇 2026 年讲解的共识，不是某一家厂商的口号）：

1. **先建 50–100 个真实问题 + 标准答案块的测试集**，再改任何参数；没有它，任何“提升 20%”都无法归因；
2. **阈值要来自测试集**：RAGAS 一类框架给出的经验参考是——Context Precision 低于 0.6 说明检索本身坏了，Faithfulness 低于 0.7 说明模型在绕过上下文编造；这两个数是参考线，不是及格线；
3. **每次改动只改一个变量**：换切块、换嵌入模型、大幅更新语料，都会让旧的评测失效，必须重跑测试集；
4. **分开看“找得到”与“答得住”**：recall 上去了、答案还没好，问题在生成侧；recall 没上去，改提示词是浪费时间。

## 七、什么时候不要用 RAG

RAG 不是万能钥匙，四种情况要先排除：

- **语料小到能直接塞进上下文时**：100 页以内的手册，直接全量放进 128K 上下文，往往比切块检索更连贯、更适合多跳推理；AIFoss 的建议是“100 页以下先试全量上下文”；
- **知识稳定、要内化的是行为与风格时**：客服话术、品牌语气、特定推理套路，更适合微调；RAG 管“事实会变”，微调管“行为要稳”，两者互补；
- **数据变化快于索引速度时**：每小时都在变的操作数据，需要真正的搜索集成（Elasticsearch、数据库全文检索）与块失效、去重、重嵌机制，而不是批量索引的向量库；
- **问题本身需要多跳复杂推理时**：小模型（8B 级）在“跨多个块拼答案”上会先掉链子，这时瓶颈是模型推理能力，不是检索复杂度——换更大的模型比堆更多检索技巧更有效。

## 八、给 Patrick 的实用启示与起步清单

**如果你只想先搭一个能用的个人/小团队 RAG，起步栈可以很轻：**

| 层 | 起步选择 | 备注 |
|---|---|---|
| 切块 | 层级切块（128 子块 / 512 父块），标题路径作前缀 | 先按结构切，再考虑语义切块或上下文前缀 |
| 嵌入 | 本地可选 nomic-embed-text v1.5（CPU 可跑、8K 上下文）；中文与多语言语料优先看 BGE-M3 | 嵌入模型与语料领域不匹配时，失败看起来像“模型问题”，其实是检索问题 |
| 向量库 | 开发用 Chroma（进程内、易重置）；团队生产用 Qdrant（索引层过滤、稀疏向量原生支持）；已有 Postgres 且向量 < 50 万可用 pgvector | 库的选择在原型期不重要，在生产期主要看过滤与扩展 |
| 检索 | BM25 + 向量混合，RRF（k=60）融合 | 两路同时做权限/租户过滤 |
| 重排 | 候选 50 → 交叉编码器留 5–10 | 只有当“引用了错误章节”或 Context Precision 低于参考线时才加 |
| 评测 | 50–100 个真实问题测试集 + recall@k / Faithfulness | 每次改动重跑，拒绝“感觉变好了” |

**动手清单（按顺序做，不要跳步）：**

- [ ] 先写 50 个你真正会问的问题，并标出每个问题的标准答案块；
- [ ] 测基线 recall@5 与 recall@10，再决定是修切块、加混合检索，还是加排序；
- [ ] 系统提示词与工具定义尽量固定、放前面（这同时帮到服务端前缀缓存与检索稳定性——见 10 月 30 日推理优化报告）；
- [ ] 把每次都会变的用户 ID、时间戳移出前缀，避免缓存与检索同时失效；
- [ ] 给系统加一条“找不到就说找不到”的显式规则，并用测试集标定触发阈值；
- [ ] 权限过滤写在检索层，不写在提示词里；两路检索用同一套过滤条件；
- [ ] 上线后定期重跑测试集：语料一变，旧的评测结论就可能过期。

**一个可以直接试的小实验：** 拿同一份 20 页文档做两组对照——A 组固定 512 token 切块 + 纯向量检索，B 组标题对齐切块 + 混合检索 + 重排；用 20 个真实问题测 recall@5。如果 B 组没有明显更好，说明你的语料本身不适合这套组合，换语料或换问题集再测，不要直接上生产。

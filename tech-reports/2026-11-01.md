# 每日 AI 技术报告 · 2026-11-01

**日期：** 2026 年 11 月 1 日（星期日）
**今日技术主题一句话概括：** MoE 不是“参数越多越便宜”，而是把账算到了三个不同的地方——算力按激活参数算、显存按全部参数算、延迟按最忙的那块 GPU 和两次全互联通信算。

> 说明：本报告基于 2026 年 11 月 1 日通过浏览器阅读的公开资料写成，包括 MoE 推理讲解、负载均衡与专家并行部署深挖、DeepSeek-V2/V3 与 DeepSeekMoE 论文要点、Switch Transformer 数学讲解。文中凡是单篇论文、单家厂商博客或单次测量的数字，均已标注来源与条件，不是通用结论；凡是“某来源的建议”，均已说明适用边界。

## 一、通俗解释：MoE 不是“请很多专家一起开会”，而是“每句话只找两三个专家问”

想象一家医院：

- **稠密模型：** 每个病人都要经过全院所有科室，哪怕只是问一句“今天天气怎么样”。科室越多，问一句话越贵。
- **MoE 模型：** 门口有个分诊员（路由器），看一眼病人的症状，只把他送到两三个最相关的科室；其他科室当天不用出诊，但工资照发、房间照留——因为下一个病人可能就需要他们。

这就是 MoE 的全部 trade-off，一句话讲完：

- **算力省了：** 每 token 只跑被选中的几个专家，计算量按“激活参数”算；
- **显存没省：** 所有专家都必须常驻显存，否则分诊员一指过去，专家不在岗，延迟就崩了；
- **协调变难了：** 专家分散在多块 GPU 上，每层都要把 token 送过去、把结果拿回来，还要保证没有哪块 GPU 被“热门专家”拖垮。

昨天的 RAG 报告讲的是“Agent 凭什么资料干活”；今天讲的是“干活的模型本身，为什么越大越不像越大”——因为“大”在 MoE 里被拆成了总量、激活量与通信量三本账。

## 二、一层到底：路由器、门控权重与“专家”到底是什么

### 1. 一层 MoE 的标准流程

在 Transformer 里，MoE 通常只替换每个 block 里的前馈网络（FFN），注意力层一般保持稠密。一个 MoE 层有 N 个结构相同的专家 FFN，外加一个很小的路由器：

1. token 的隐藏表示进入路由器——一个线性层，输出每个专家的分数；
2. 取分数最高的 k 个专家（top-k，常见 k=1 或 2，DeepSeek-V3 是 8）；
3. 只有这 k 个专家真正计算，其余专家对该 token 不做功；
4. 各专家输出按路由器分数归一化后的权重加权求和，成为该层输出；
5. 下一层重新路由：同一个 token 在不同层可以走不同的专家，同一句话里的两个 token 在同一层也可以走不同的专家。

路由器本身的计算量相对专家可以忽略不计，省下来的算力全部来自“只跑 k 个而不是 N 个”。

### 2. 两个必须纠正的直觉

**第一，“专家”不等于“学科”。** Mixtral 的作者发现，其专家并没有按生物、哲学这类主题清晰分工，路由更多跟随句法——例如 Python 代码里的 `self` 与缩进 token 倾向于走同一批专家。把专家想象成“数学专家、法律专家”是方便的比喻，但不是训练保证的结论；专家分工是训练中涌现的 loose specialization，不是事先指定的岗位。

**第二，路由器分数有两个用途，不要混用。** 在 DeepSeek-V3 的无辅助损失设计里，偏置只影响“选谁”（top-k 的排序），而不影响“权重是多少”——门控权重仍来自原始亲和分数。这一点在第三节会展开：它正是“既要均衡、又不扭曲模型计算”的关键。

### 3. DeepSeekMoE 的两处改进：切得更细、把公共知识单独拎出来

传统 MoE（例如 GShard 的 top-2）的问题是：专家太粗，组合方式太少；而且每个专家都要重复学标点、语法这类公共知识，造成冗余。DeepSeekMoE 做了两件事：

- **细粒度切分：** 把每个专家按中间维度切成 m 份，专家数从 N 变成 mN，每 token 激活数从 K 变成 mK。在总参数与计算量不变的前提下，组合方式变多了，路由可以更精细地拼出“这个 token 需要的能力组合”。
- **共享专家隔离：** 单独留出 Ks 个共享专家，每个 token 都必经它们，专门承载公共知识；相应地，路由专家的激活数减少 Ks 个，保持总计算量不变。于是路由专家不必再人人重复学公共部分，可以更专注于差异化知识。

DeepSeek-V3 就是这套思路的放大版：256 个路由专家 + 1 个共享专家，每 token 激活 8 个路由专家。论文在 2B 规模上的对照结论是：DeepSeekMoE 2B 可与参数量与计算量更大的 GShard 2.8B 相当——但这是论文在特定语料与评测上的结论，不是“细粒度在所有场景都更优”的通用保证。

## 三、数字对照：先看清“总量”与“激活量”是两本账

| 模型 | 总参数 | 每 token 激活 | 专家 / top-k | 来源口径 |
|---|---|---|---|---|
| Mixtral 8x7B | 47B | 约 13B | 8 / 2 | 多篇讲解一致 |
| DeepSeek-V3 | 671B | 37B | 256 路由 + 1 共享 / 8 | 技术报告 |
| DeepSeek V3.2 Speciale | 685B | 37B | 256 / 8 | 厂商博客整理 |
| Llama 4 Maverick | 400B | 17B | 128 / 1 | 厂商博客整理 |
| Kimi K2 | 1T | 约 32B | 384 / 8 | 厂商博客整理 |
| Mixtral 8x22B | 141B | 39B | 8 / 2 | 厂商博客整理 |
| Mistral Large 4（对照） | 约 1T | 约 52B | 128 路由 / 4 + 1 共享 | 10 月 30 日报告的模型卡口径 |

读这张表只记住一个公式就够了：

```
显存 ∝ 总参数（所有专家都要常驻）
算力 ∝ 激活参数（每 token 只跑 k 个专家）
```

一个 8 专家、每 token 激活 2 个的模型，显存是同等激活量稠密模型的约 4 倍，算力却只有约 2/8。Spheron 的厂商指南把这一点算得更直白：DeepSeek V3.2 Speciale 在 FP8 下光权重就约 685GB，8 张 H200 才能装下；Kimi K2 在 FP8 下约 1TB，即使 8 张 H200 也装不下，必须跨节点——这还只是权重，没算 KV 缓存与激活开销（指南建议再加约 15%  overhead，生产还要再留 20%–40% 的余量）。所以“能不能跑 MoE”首先不是算力问题，而是“显存够不够把全部专家一次性装下”的问题。

注意一个例外：KV 缓存不按总量算，而按激活架构算。DeepSeek-V3 的 KV 缓存规模由其 37B 级激活架构决定，而不是 671B 总量；再叠加 MLA 这类压缩注意力，KV 还能进一步缩小。这也是为什么“显存大”与“长上下文便宜”可以在同一个模型里同时成立——它们算的是不同的账。

## 四、最难的一关：负载均衡——四个杠杆，各有代价

路由器是学出来的，而语言建模损失本身并不要求它“公平分活”。早期某个专家多拿一点 token，就会多拿梯度、学得更快、分数更高、再多拿 token——这叫自强化，最终就是路由崩塌：少数专家过载、其余专家闲置甚至死亡。训练与推理各有一套表现：训练时是步时间被拖慢，推理时是某块 GPU 成为瓶颈。

衡量不均衡，先看四个数（按层、按步测，平均值会掩盖最差的一层）：

- 每个专家的 token 数 max/mean；
- 每个 GPU 的 token 数 max/mean——这才是真正决定步时间的数；
- 容量限制下的丢弃率；
- 零 token 的死专家数。

四个杠杆的对照如下：

### 杠杆 1：容量因子与丢弃——最老、最直白，但丢的是“最擅长”的 token

Switch Transformer 的容量公式是：

```
专家容量 = (每批 token 数 / 专家数) × 容量因子
```

top-k 时分子再乘 k。容量因子 1.0 表示“刚好均分”，1.25 表示留 25% 的余量。超过容量的 token 不排队、不重路由，直接跳过该层专家、只走残差连接。top-1 时被丢的 token 在该层完全没有 FFN 贡献；top-k 时通常还有另一个专家兜底，损失是部分的。

代价很清楚：丢弃是静默的质量损失，而且恰恰集中在“热门专家最擅长”的那批 token 上。AICassindra 的模拟给了一个具体量级：4096 token、64 专家、top-8 时，均分是每专家 512 个分配；容量因子 1.25 下容量为 640，未经均衡时最忙专家拿到 856 个、丢弃 2.37%；控制器收敛后最忙专家降至 567 个、丢弃归零。这组数字来自模拟，不是生产实测，但它说明了“均衡”与“丢弃”之间的换算关系。

### 杠杆 2：辅助损失——简单、经典，但与主损失抢方向

Switch 的辅助损失是：

```
L_aux = α · N · Σ f_i · P_i，α = 0.01
```

其中 f_i 是实际分发到专家 i 的 token 比例（硬计数、不可微），P_i 是该专家在批内的平均路由概率（可微）。它的梯度通过 P_i 起作用：观察到的过载成为系数，把概率质量从过载专家推开。均匀分布时该损失取最小值。

问题也在这里：α 太大，均衡了但损害主任务质量；α 太小，均衡不住。ST-MoE 还加了一个 router z-loss（路由 logits 的平方 log-sum-exp，系数 0.001），但它主要是防止 logits 数值爆炸，而不是直接均衡负载。辅助损失是“用一个与主目标冲突的梯度去纠偏”，这正是下一杠杆要绕开的点。

### 杠杆 3：偏置控制器——DeepSeek-V3 的无辅助损失均衡

DeepSeek-V3 的做法是：给每个路由专家一个偏置 b_i，只加在“选谁”的亲和分数上，不加在“权重是多少”的门控值上。训练每步结束时：

- 过载专家的偏置减 γ；
- 欠载专家的偏置加 γ。

报告中的 γ 在前 14.3T token 为 0.001，最后 500B token 冻结为 0（偏置不动、路由权重继续训练）；同时保留一个系数仅 0.0001 的序列内均衡损失，只防单个序列内的极端不均衡。

为什么这招值得单独讲？因为偏置不是用梯度下降训练的，而是一个基于符号的积分控制器——它不与语言建模损失抢梯度，也不扭曲门控权重。代价同样真实：γ 太大，偏置来回震荡；γ 太小，跟不上数据分布的变化；而且模拟显示，即使收敛后 max/mean 也只从 1.67 降到约 1.1 左右、不会到 1.0——因为每步的符号更新与批采样的随机性都会留下残差。所以偏置控制器之后，仍需要容量余量或无丢弃内核来兜底。

### 杠杆 4：摆放与复制——推理侧不用重训就能动的杠杆

推理时不能重训路由器，但可以动“专家住在哪”：

- **打散热门专家：** 同样四个热门专家，放在同一块 GPU 上与分散到四块 GPU 上，专家 max/mean 相同，GPU max/mean 却天差地别。模拟中，64 专家在 8 GPU 上连续摆放时，专家比 1.67 对应 GPU 比 1.20；均衡后 GPU 比降至 1.02；按实测负载摆放还能进一步优化。
- **节点受限路由：** DeepSeek-V3 规定每 token 至多发往 4 个节点，限制跨节点流量。
- **冗余专家复制：** 把热门专家复制到多个 GPU 上分流。DeepSeek-V3 在 prefill 部署 32 个冗余专家，热门专家按线上统计定期调整；开源 EPLB 库就是按负载估计算这份摆放计划的工具。但要注意：EPLB 只负责“怎么摆”，不负责“预测负载”——它建议用历史滑动平均，预测本身仍是部署方的责任。

**一个容易踩的坑：** 恢复检查点时如果丢了路由偏置，路由会静默改变。偏置是模型的一部分，必须随权重一起保存。

## 五、推理部署：专家并行、张量并行与流水线并行怎么选

| 并行方式 | 切什么 | 通信模式 | 适用场景 |
|---|---|---|---|
| 专家并行（EP） | 整个专家分到不同 GPU | 每 MoE 层两次 all-to-all：dispatch 送过去、combine 拿回来 | 专家多、单专家能装进单卡、节点内高速互联 |
| 张量并行（TP） | 每个权重矩阵内部切分 | 每层约两次 all-reduce | 单个专家太大、或要压低 prefill 延迟 |
| 流水线并行（PP） | 不同层分到不同阶段 | 阶段间顺序传递 | 显存是唯一瓶颈时；交互延迟不友好，有气泡 |

生产里常见的是组合：节点内用张量并行、跨节点用专家并行；或者像宽专家并行（wide-EP）那样，注意力层按数据并行跑（每 GPU 独立 batch 与 KV 缓存、无跨卡通信），MoE 层按专家并行跑（TP=1 时 EP 规模等于数据并行规模）。llm-d 的宽 EP 文档强调两点：dispatch/combine 是稀疏的 all-to-all——只发给被选中的专家 rank，带宽消耗低于张量并行的 all-reduce；但每 MoE 层都是全组同步点，任何一 rank 变慢，全组都等它。

### 一个可复算的显存例子：DeepSeek-V3，FP8

按 AICassindra 部署深挖的测算（隐藏维度 7168、专家中间维度 2048、每专家 gate/up/down 三个矩阵）：

- 单个专家单层约 44M 参数，FP8 下约 44MB；
- EP=16 时，每 GPU 每层 16 个专家，58 层 MoE 共约 41–43GB；
- 再加注意力、共享专家、稠密层、embedding 与输出头约 17GB（该文的工作估计值，需在自己的构建上实测）；
- 80GB 显存、90% 利用率下，每 rank 约剩 12GB 给 KV 缓存；
- EP=32 时，每 rank 约 9 个专家/层，KV 余量约 32GB——代价是多一倍节点，且每 token 的 8 个专家目的地中约四分之三在其他节点（EP=16 时约一半）。

这就是“EP 越宽，KV 越宽裕、跨节点流量越大”的换算。选 EP 不是选“越大越好”，而是选“刚好装下目标上下文与并发数”的最小宽度。

### 后端与阶段：decode 与 prefill 要的不是同一种 all-to-all

- decode：每步 batch 小、消息小，延迟主导，适合 DeepEP 的低延迟后端；
- prefill：消息大、吞吐主导，适合高吞吐后端；
- 没有 DeepEP 时可用 allgather+reducescatter 作为可移植默认，但扩展性较差。

如果把 prefill 与 decode 拆成两个部署（中间用 KV 传输衔接），两者可以各用各的后端、甚至各用各的 EP 规模；如果混跑，就按主导延迟目标的那一相来选。

### 单个 EP 组就是单个故障域

这是宽 EP 与稠密数据并行最本质的区别：稠密 fleet 掉一块 GPU，只损失一个副本的容量；宽 EP 里每 rank 都持有其他 rank 需要的专家，任何一 rank 崩溃、挂起或变慢，都会卡住每一层、每一 rank。由此得到三条运维结论：

- 健康检查必须是组级别的：负载均衡器应在任一 rank 不健康时绕开整个部署；就绪检查应跑一次真实前向，而不只是看 HTTP 端口通不通；
- 重启是组级别的：换版本要整组起新组、冒烟测试、切小流量、对比 p50/p99 后再排空旧组；组内逐 rank 滚动升级不是受支持的模式；
- 容量按组算：有可用性目标的服务，至少跑两个独立 EP 组，互为备份；同时要对“单 rank 步时间扩散”告警，因为发热降频、网卡误码这类“没崩但变慢”的 straggler，同样会拖垮全组。

## 六、常见坑：按这份清单自查

- **按激活量去买显存。** 买卡、租卡、做容量规划时，总参数 × 精度字节数才是起点；激活量只决定算力与 KV 规模，不决定权重显存。
- **小批量下 MoE 并不省。** batch 很小时，只有两三个专家被激活，但 dispatch/combine 的 all-to-all 开销照付；MoE 的甜点是大批量、高吞吐、互联够好的场景，单用户低延迟小请求反而可能不如同等激活量的稠密模型划算。
- **量化要按专家做，不能一刀切。** 不同专家对量化的敏感度不同：热门专家冗余度高、冷门专家可能承载小众模式，激进量化会不成比例地伤到后者。厂商指南提到的“热门专家 FP8、冷门专家 INT4/INT2”动态量化，能在不重训的前提下降 30%–50% 显存——但这是厂商指南口径，落地前必须在自己的评测集上按专家验证质量，而不是直接照搬比例。
- **把路由当作“可解释的主题标签”。** 专家分工是涌现的、按句法与统计模式组织的，拿它做“这段回答来自法律专家”之类的归因，是过度解读。
- **丢弃率不记录、不告警。** 容量限制下的丢弃是静默的；评估时换了容量因子而不记录丢弃率，质量变化就无法归因。部署时要把每层丢弃率、死专家数、GPU max/mean 一起上仪表盘。
- **只测平均延迟，不测 p99 与重均衡时刻的延迟。** EPLB 重摆放会搬权重、产生延迟毛刺；上线前要在重均衡事件附近单独看 p99，而不是只看日常 p50。
- **注意力与 MoE 的账混在一起。** KV 缓存按激活架构算，权重显存按总量算，通信按每层两次 all-to-all 算——三本账分开，才不会出现“参数小所以一定便宜”或“参数大所以一定跑不动”的误判。

## 七、给 Patrick 的实用启示与起步清单

**如果你只是调用 API，不用自己部署：**

- 问服务商两个数就够了：总参数与激活参数。只给其中一个数的“大模型”宣传，先打个问号。
- 长上下文任务优先看 KV 相关设计（例如是否用 MLA 这类压缩注意力），而不是只看总参数；短对话、低延迟任务优先看单请求延迟与首 token 时间，而不是只看吞吐。

**如果你想自己跑一个 MoE，先从小规模验证这条链路：**

| 步骤 | 做法 | 验收标准 |
|---|---|---|
| 选模型 | 从 Mixtral 8x7B 或同级 Qwen MoE 起步，单节点或双卡先跑通 | 能稳定出结果，且显存占用与“总参数 × 精度”测算对得上 |
| 测负载 | 打开路由统计，看每专家 token 数、GPU max/mean、死专家数 | 不只看平均，要看到最忙的一层与最忙的一块卡 |
| 压批量 | 对比 batch=1 与 batch=64 的单 token 延迟与吞吐 | 确认 MoE 在你的流量形态下是否真的比同级稠密模型划算 |
| 试量化 | 先整体 FP8/INT4，再按专家分组校准 | 质量回归集上，冷门任务（小众语言、长尾代码）不出现不成比例的下跌 |
| 做故障演练 | 模拟一 rank 变慢或重启，观察整组表现 | 确认负载均衡器能绕开整组，而不是只摘掉一块卡 |

**一个可以直接试的小实验：** 用同一个提示词集，对比“固定切块+纯向量”的 RAG（10 月 31 日报告）与今天的 MoE 部署问题——前者问“资料找对了没有”，后者问“模型跑起来贵在哪里”。把两者合起来读，Agent 从 demo 到长期运行的账本就齐了：Harness 决定干什么、RAG 决定凭什么资料干、MoE 推理决定干起来花多少钱与多少显存。

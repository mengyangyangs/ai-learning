# 每日 AI 技术报告 · 2026-11-03

**日期：** 2026 年 11 月 3 日（星期二）
**今日技术主题一句话概括：** 推测解码不是“让模型变聪明”，而是“让大模型少跑冤枉路”：小草稿先猜几个 token，大模型一次验完，只保留它自己本来就会输出的那部分——输出分布不变，省下的是反复搬运权重的等待时间。

## 一、通俗解释：草稿员先写，主编一次审——审得快，是因为主编本来就要把整本书翻一遍

想象你要请一位主编（大模型）逐字写一篇文章：

- **普通写法：** 主编每写一个字，都要把整本参考书（模型权重）从书架搬到桌上、翻一遍、再放回去。写 100 个字，就要搬 100 次书。搬书的时间，远大于写字本身的时间。
- **推测解码的写法：** 先请一位实习生（草稿模型）快速写出接下来 5 个字的草稿；主编只搬一次书，顺手把这 5 个字全审一遍：对的留下，第一个错的改成主编自己的写法，错的后面全部作废、下一轮重猜。于是主编搬一次书，能产出 3–4 个字，而不是 1 个。

这里有两个关键点，先讲清楚，后面就不会被“加速”这个词误导：

1. **省的是“搬书”，不是“写字”。** 大模型解码在 batch 很小时是显存带宽受限：每生成 1 个 token，都要把全部权重从显存读一遍，算术单元大部分时间在等数据。一次前向验 5 个 token，权重也只需读一遍——多出来的 token 计算，用的几乎是本来就闲置的算力。
2. **主编没有被“带偏”。** 接受规则不是“草稿写什么就信什么”，而是一套修正拒绝采样：草稿 token 被接受的概率是 min(1, p_target / p_draft)，被拒绝时从残差分布 norm(max(0, p_target − q_draft)) 里重采样。数学上，这保证输出分布与大模型单独生成完全一致——推测解码是无损加速，不是近似加速。这一点与量化、蒸馏、剪枝有本质区别：后三者都以质量换速度，推测解码不换。

一个数字例子能把带宽账算清楚（AICassindra 工程深挖的测算口径）：70B 模型 fp16 权重约 140GB，显存带宽 2TB/s 时，单步下限约 70ms（约 14 token/s）；1B 草稿约 2GB，约 1ms/步；5 步草稿（5ms）+ 1 次验证（70ms）= 75ms，若期望接受 3.5 个 token，则约 47 token/s，约 3.3 倍。所有后续设计，都是在“如何提高期望接受长度、而不抬高那 70ms”上做文章。

## 二、核心循环：草稿、验证、接受、修正——四步里只有一步真正花钱

### 1. 标准循环（以草稿长度 γ 为例）

1. **草稿：** 草稿机制自回归生成 γ 个候选 token（常见 γ = 3–8，Morph 整理中 n-gram 草稿可用到 64 的窗口，但那是另一类草稿，见第四节）。
2. **验证：** 目标模型对“上下文 + γ 个候选”做一次前向，得到每个位置上自己的分布。注意是 γ+1 个位置：每个候选位置一个分布，再加一个“如果全部接受，接下来是什么”的分布。
3. **接受：** 从左到右逐个检查，接受概率为 min(1, p_target / p_draft)。第一个拒绝即停，后面的候选全部作废——哪怕后面的草稿其实是对的，也因为前缀已断而不能用。
4. **修正与奖励：** 在拒绝处，目标模型从残差分布中采样一个修正 token；如果 γ 个全被接受，验证前向还会额外产出 1 个“奖励 token”（bonus token）。于是每轮产出 token 数在 1 到 γ+1 之间，期望值记为 τ（mean accepted length，含奖励 token）。

### 2. 接受率、草稿长度与草稿成本：三者决定一切

在“各位置接受相互独立”的简化假设下，Leviathan 等（Google Research，arXiv 2211.17192，ICML 2023）给出了期望接受长度与加速比的公式。记 α 为平均接受率（目标接受一个草稿 token 的概率）、γ 为草稿长度、c 为单步草稿成本与单步目标成本之比：

```
期望接受长度  τ = Σ_{i=0}^{γ} α^i = (1 − α^{γ+1}) / (1 − α)
加速比 ≈ τ / (γc + 1) = (1 − α^{γ+1}) / ((1 − α)(γc + 1))
```

这条公式有三个直接推论，值得背下来：

- **天花板由 α 定，不由 γ 定。** γ 再大，加速比也超不过 1/(1−α)：α = 0.9 时天花板是 10 倍，α = 0.7 时只有约 3.3 倍，α = 0.5 时只有 2 倍。草稿猜不准时，加长草稿没有用。
- **γ 有最优值，不是越大越好。** γ 增大时，分子 τ 趋向天花板而增长放缓，分母 γc 却线性增长；过了最优值，每多一个草稿 token 几乎都会被拒绝，却照付草稿成本。vLLM 2026 年 8 月在 MI300X/MI355X 上对 Qwen3-8B + EAGLE-3、GSM8K 的扫掠把这条曲线测了出来：γ=1 时只有 0.71 倍（比不推测还慢）、γ=3 时 0.99 倍、γ=5 时 1.18 倍、γ=7 时 1.17 倍——首位置接受率 86%，第 7 位置仅 19%，越往后的草稿越不值钱。
- **高接受率不充分，c 过大同样拖垮加速。** 同一模型与草稿在 MATH500 上，γ 扫掠始终未超过基线，尽管首位置接受率 89%（高于 GSM8K 的成功案例）。原因在分母：草稿本身太贵时，即使猜得准，加速比也会跌破 1。只报接受率、不报草稿成本的加速宣称，是不完整的。

原始论文的实测锚点（均为论文口径、batch 较小的设定）：Leviathan 等在 T5-XXL 上 2–3 倍（翻译任务温度 0 时 3.4 倍、温度 1 时 2.6 倍；摘要 3.1 倍与 2.3 倍）；DeepMind 的 Chen 等（arXiv 2302.01318）在 Chinchilla 70B 上 2–2.5 倍；EAGLE 在 LLaMA2-Chat 70B 上 2.7–3.5 倍；EAGLE-2 为 3.05–4.26 倍；EAGLE-3 最高 6.5 倍。温度的影响贯穿其中：温度越高，目标分布越不可预测，α 越低——贪心解码最容易加速，高温创意写作最难。

### 3. “无损”三个字要打两个补丁

理论上的无损，是“分布相同”；工程上的现实，是“字节不一定相同”。这一点在 2026 年的工程整理里被反复提醒，值得单独写出来：

- **浮点精度会翻转近 tie 的选择。** NeurIPS 2026 教育教程的一个实测：同一 Qwen3-8B 贪心解码，普通路径与 DSpark 推测路径的 HTML 输出在前 8299 个字符完全相同（占 76%），随后在一个近 tie token 处分叉（`transition: color 0.2s` 变为 `0.3s`），最终长度 10924 对 10535 字符。解释是：推测路径用了不同的 kernel，logits 在浮点精度内漂移，近 tie 的 argmax 倒向另一边。仅改变 batch 大小，也能造成同样的分叉。
- **量化会放大这个差距。** llama.cpp 的一份矩阵测试称：Q4_K_M 目标上，基于模型的草稿会偏离普通贪心输出，而 n-gram 推测在相同权重上保持一致；bf16 目标上，同一草稿四次运行全部一致。结论是：分布仍是目标的分布，但“与非推测运行字节相同”这件事，引擎并不承诺——vLLM 文档也把保证拆成三层：理论无损（受硬件数值精度限制）、算法无损（拒绝采样收敛测试通过）、输出稳定性“不承诺”。

对评估与复现的影响是直接的：如果你要“两次运行结果完全一致”作为验收标准，推测解码（以及 batch 大小、kernel 选择）本身就是变量；验收时应固定引擎、配置与 batch，或接受统计等价而非字节等价。

## 三、草稿从哪里来：五种来源，成本与精度各不相同

| 草稿来源 | 做法 | 优点 | 代价与边界 |
|---|---|---|---|
| 独立小模型 | 同族小模型（如 1B 带 70B）自回归生成 γ 个 token | 通用、无需改目标模型 | 须共享 tokenizer 与词表；成本比 c 须在约 0.01–0.05 区间（7B 带 13B 几乎必亏）；多一套权重、KV 缓存与调度 |
| Prompt-lookup / n-gram | 用已生成文本的尾巴在 prompt（或生成历史）中找续写，零参数 | 零权重、零带宽；在摘要、RAG、代码编辑、改写这类“输出多为复制输入”的任务上极有效 | 只在重复性文本上有效；开放式生成几乎无命中 |
| Lookahead | Jacobi 式并行更新 + 从中收获 n-gram 池，再验证池命中 | 无需训练任何组件 | 命中率依赖文本重复性；实现较绕 |
| Medusa 多头 | 在目标最后隐藏层上加 k 个轻头，头 i 预测 t+i+1 位置（见下） | 无需第二模型、无 tokenizer 错配、读的是目标自己的隐藏状态 | 各头彼此独立预测，精度随 i 陡降；需树 + 宽松接受规则补救 |
| EAGLE 特征头 | 用单层 decoder 自回归预测目标的隐藏特征，再经目标 LM head 解码（见下） | 接受率最高；草稿头仅约目标一层大小 | 须针对每个目标、每种精度重训；训练与推理的暴露偏差须专门处理 |
| 原生多 token 预测头（MTP） | 训练时就让模型同时预测未来多个 token（如 DeepSeek-V3 的 MTP，报 1 个额外 token、85–90% 的第二 token 接受率、约 1.8 倍 token/s） | 草稿能力是模型自带的，不用外挂 | 改变训练目标；加速幅度受限于头的数量与训练方式 |

### 1. 独立草稿的 tokenizer 陷阱：最常见、最致命

验证是在“同一位置、同一 token id”上比较目标分布 p(x) 与草稿分布 q(x)。如果两个模型 tokenizer 不同，草稿的 3 个 token 可能根本对应不上目标的任何前缀，分段方式一变，位置对齐就无从谈起。Llama 2（32k 词表）与 Llama 3（128256 词表）即使同名“同族”，跨代也不能直接配对。跨 tokenizer 的变通方案（detokenize 再 re-tokenize、或在共享子词交集上映射）都增加每步 CPU 工作并压低接受率。工程上的结论很干脆：**找不到共享 tokenizer 的小模型时，优先考虑自推测（Medusa/EAGLE）或无模型草稿，而不是硬凑一个外来小模型。**

### 2. Medusa：多个头并行猜，再用树一次验完

Medusa（Cai 等，2024，arXiv 2401.10774）的做法是：在骨干模型的最后隐藏层上，加 k 个轻量解码头（每头为 SiLU + 残差的前馈 + 词表投影，论文称 5 个头已够）。头 k 读同一个隐藏状态，预测 t+k+1 位置的 token——也就是说，一次前向就能同时得到“下一个、再下一个、再再下一个”的猜测，无需逐 token 自回归。

它的两个配套机制决定了成败：

- **树注意力（tree attention）：** 各头的 top-k 猜测组合成候选树（例如头 1 取 top-2、头 2 取 top-3，笛卡尔积得 6 条候选，共享前缀构成树）。验证时把整棵树展平为一个序列，但注意力掩码只允许每个节点看见自己的祖先（不见兄弟与堂兄弟），position id 取节点深度——于是每个候选路径都像“唯一续写”一样被评分，一次前向验完所有分支。稀疏 64 节点树在论文整理中优于稠密 256 节点树：树越大，验证成本与 KV 占用线性增长，收益却递减。
- **接受规则的取舍：** Medusa 可用标准拒绝采样（保分布），但论文主推 typical acceptance——一个随熵自适应的置信阈值：只保留“合理”的候选，换取更长的接受长度。代价是：温度大于 0 时不再分布精确；温度为 0（贪心）时仍精确。Medusa-1 仅训练新头、冻结骨干，报 2.2 倍以上加速；这是“不改目标模型、只加几个头”的最小侵入路线。

Medusa 的结构性弱点也在这里：头 i 预测时看不见 t+1…t+i 的采样结果，精度随 i 陡降——越往后的头，猜得越差。EAGLE 正是为修这个弱点而生的。

### 3. EAGLE：不在 token 层猜，而在特征层“滚”

EAGLE（Li 等）的洞见是：特征空间比 token 空间更平滑、熵更低，因此用一个很小的头在特征层做自回归，比在 token 层猜要准得多。递推式写出来只有四行（AICassindra 深挖的记号，f_i 为目标次顶层隐藏状态）：

```
x_i    = concat( f_i , emb(t_{i+1}) )     # [2d]：特征 + 刚采样 token 的 embedding
h_i    = fc( x_i )                        # [2d] -> [d]
f'_{i+1} = DecoderLayer( h_i , cache )   # [d]：预测的下一个特征
t_{i+2}  ~ softmax( LM_head( f'_{i+1} ) ) # 用目标冻结的 LM head 解出下一个 token
```

头内只有 fc（2d×d）与一层 decoder（约 12d²），合计约等于目标的一层（目标的 1–2%），且共享目标的 embedding 与 LM head，不新增大权重。预测出的特征再扮演下一轮的 f，滚 γ 步即得一条草稿链；token 始终由目标自己的 LM head 解出，因此草稿分布天然锚定在目标上。

- **EAGLE-1 的补丁与天花板：** 训练时喂的是目标的真实特征，推理时喂的是自预测特征——经典暴露偏差（exposure bias），越深漂移越大。EAGLE-1 用训练时加噪声 + 保持草稿较浅来缓解，这是补丁而非根治；特征漂移正是“存在最优草稿深度、而非越深越好”的结构性原因。
- **EAGLE-2 的 expand-and-rerank：** 不再只用一条链，而是动态长树。Expand 阶段按路径价值（沿路 draft 置信度的乘积，即该前缀被接受的概率估计）贪心扩展最高价值的叶节点；Rerank 阶段汇集全部节点、取价值最高的 top-m 去验证。验证预算 m 固定，EAGLE-2 只是把同一预算花在更可能被接受的地方。树改变接受长度的算法：单链期望为 (1−α^{γ+1})/(1−α)；树在每层提供 b 个候选时，至少一个被接受的概率升为 1−(1−α)^b——α=0.7、b=3 时，深度 2 的到达概率从 0.49 升至约 0.97。树是用“对冲一次倒霉拒绝”来买接受长度，而验证预算不变。
- **EAGLE-3 的两处关键改动：** 第一，**去掉特征回归损失**。EAGLE-1/2 要求草稿头预测目标次顶层特征（回归损失把预测特征拉向真实特征），但这正是天花板：单层头把高维特征向量拟合到一定程度后，加数据不再提升接受率。EAGLE-3 直接训 token 预测——预测特征从来不是目的，预测被接受的 token 才是。第二，**training-time test（训练时测试）**：训练时模拟多步自回归，让头消费自己预测的中间输出、并在每一步接受 token 监督，直接消除训练/推理 gap，代价是每样本要展开多步、训练更贵。第三，**多层特征融合**：不再只读次顶层单一特征，而是把低、中、高层的隐藏状态 concat 后投影（低层多词法/位置信号、高层多语义与 next-token 承诺），复用目标验证前向中已算出的激活，不增加目标算力。三者合起来，接受率可随数据规模继续提升，EAGLE-3 报最高 6.5 倍、约比 EAGLE-2 再快 1.3–1.4 倍，在 SGLang batch 64 下仍有 1.38 倍吞吐提升（论文口径）。

EAGLE 的坑也要同时写上：**每目标、每精度须重训**——fp16 目标上训的头，用到 int4 目标上会因特征漂移而掉接受率；树过大时验证成本与 KV 占用线性增长，过了最优点，接受长度微升、吞吐反降；接受率随负载分布变化，换了流量分布就要重测、重调。

## 四、工程侧：KV 回滚、连续批处理与长上下文——论文不写、生产必踩的三件事

### 1. KV 缓存手术：拒绝的 token 必须“消失”，否则就是静默损坏

验证会把全部 M 个推测位置的 key/value 写进目标的 KV 缓存，但只有被接受的路径是真实的，其余必须在下一步之前消失，否则模型会 attend 到它从未输出过的 token——表现为微妙的不连贯文本，而不是崩溃，极难定位。

- **线性草稿：** 缓存是追加式的，只需把长度计数器截断到“前缀 + 已接受数”，其余自然作废。
- **树草稿：** 被接受路径的条目分散在展平后的 M 个槽位里，须按层 gather 存活行并压实为连续位置；分页注意力下，这对应一次块表重写加少量槽位拷贝。草稿自身的缓存也要同样回滚。
- **并发代价：** 每条在途序列须预留 M 个槽位，而其中大部分会被丢弃——这直接降低了同一时刻能容纳的序列数，极端时还会触发抢占。

### 2. 连续批处理会吃掉加速：推测是延迟优化，不是吞吐优化

这是最容易误判的一点。推测利用的是“单流解码时算术单元闲置”这一前提；但连续批处理（continuous batching）本身已经在利用这部分闲置：batch 为 B 时，一次权重扫掠已服务 B 个 token，算术强度已是 B 倍。再加推测，每步要处理 B·M 个位置——一旦越过硬件的算存比，目标模型进入算力受限，每个推测位置都付真实时间，被丢弃的 B·(M−a) 个位置全是净亏损。加速比于是从 batch 1 时的约 E[接受长度]，一路衰减到小于 1（净变慢）。

生产上的应对是**按负载动态开关**，而不是“一开全开”：vLLM 的关键生产设置是 `--speculative-disable-by-batch-size 32`（队列深度超阈即自动回落标准解码；Spheron 指南称，无此设置时 100+ 并发下吞吐可比标准解码低 30–40%）。SGLang 与 vLLM 的旗标不同（vLLM 用 `--speculative-config` 的 JSON，SGLang 用 `--speculative-algorithm` 加 draft-tree 旗标），但开关逻辑一致：低并发保延迟，高并发保吞吐。Morph 的独立实测也给出同一条曲线：batch 1 时约 1.96 倍，batch 128 时约 1.21 倍，且已发表的扫掠中包含“比不推测更慢”的配置——调参时必须在自己的并发水平上测，而不是抄论文的 batch 1 数字。

Saguaro（Speculative Speculative Decoding，Kumar、Dao、May，arXiv 2603.03251，二手整理）试图从架构上缓解这个同步问题：把草稿与验证解耦到不同硬件、并行预判验证结果，称比现有推测引擎快约 30%、比标准自回归快最高 5 倍（Llama-3.1-70B + Llama-3.2-1B 草稿），并以自适应 batch 阈值 b* 在大 batch 下回落到 n-gram/非神经草稿。这仍是研究阶段的路线，但它指对了方向：推测的下一步不是“更准的草稿”，而是“不再让草稿与验证互相空等”。

### 3. 长上下文与 MoE：两个会悄悄改变结论的变量

- **长上下文：** 推测摊薄的是权重扫掠，不是 KV 注意力。上下文到 128k 时，注意力项占主导且随 M 放大，推测的收益会被稀释——长上下文任务要单独测，不能沿用短上下文的加速比。
- **MoE：** Cohere 的测量（日报二手）称，10 个稀疏 MoE（30B–1T、8–512 专家）中相邻 token 共享 20%–45% 的专家，因此 batch 1 下推测解码比此前预期更划算——因为验证多个候选时，专家权重被复用的比例更高。但反向的坑同样存在：SGLang 上 Nemotron-3-Super 的案例中，接受率恒为 1/(γ+1)（即每轮只接受基础 token、草稿全拒），吞吐从 14.4 降至 10.9 tok/s，后查为 MoE 激活不被 runner 支持——**接受率恒为 1/(γ+1) 是“集成坏了”的特征信号，不是“草稿弱”的信号**，应报警而非调参。
- **水印的对照：** Meta 的 TextSeal2 无失真文本水印在推测解码下信号仍保留（高斯 copula 把多把密钥合成一把虚拟密钥再加噪声，检测率 89%；前代每 token 在两把密钥中随机选一把，检测器只能取平均）。这说明“加速不改变分布”与“输出可检测”可以并存，但前提是水印设计本身考虑了推测路径——不是所有“无损”承诺都能自动带上可检测性。

## 五、选型与落地清单：先测三个数，再决定开不开

### 1. 先测的三个数（按顺序）

| 要测的数 | 怎么测 | 判据 |
|---|---|---|
| 逐位置接受率曲线 | 在代表性流量上，记录第 1、2、…、γ 位置各自的接受率 | 曲线陡降处就是 γ 的最优点；过了它，每多一个草稿位置几乎都是净成本 |
| 均值接受长度 τ 与草稿成本 c | 同一流量、同一引擎上，记录每验证通过产出的 token 数与草稿耗时占比 | 代入公式算加速比；τ 上升而加速下降时，说明树/验证成本已超过收益 |
| 并发与上下文下的加速比 | 在目标 batch（1、8、32、64）与目标上下文长度下分别测 | 只在“加速比 > 1 且稳定”的区间开启推测，其余区间自动回落标准解码 |

另有两条报警线要写进监控：接受率低于约 50–60% 即考虑关闭（AICassindra 工程深挖的经验阈值）；接受率恒为 1/(γ+1) 即查集成 bug，不要调 γ。

### 2. 按场景选草稿

- **只是调用 API，不自己部署：** 推测解码对你意味着“同一模型、同一价格下，首 token 与流式延迟可能更低”，而不是“模型变强了”。不要为“支持推测解码”多付费，除非服务商能给出你所在并发与任务类型下的延迟数据。
- **自己跑单用户/低并发服务（如本地助手、单人 coding agent）：** 这是推测最赚钱的场景。起手选 prompt-lookup（零成本）或 EAGLE-3（若有对应目标的公开头）；先测逐位置接受率曲线定 γ，再设按 batch 回落的阈值。
- **自己跑高并发在线服务：** 默认关闭或只在低负载时段开启；把推测当作“延迟优化开关”，而不是“吞吐倍增器”。EAGLE-3 在 batch 64 下仍有 1.38 倍吞吐提升的论文数字，只能在你自己的 batch 与树配置上复测后才采信。
- **自己跑长上下文或 MoE 模型：** 长上下文先测注意力占比，MoE 先测专家共享率与接受率恒值报警；两种情况都不要直接套用短上下文、稠密模型的加速比。

### 3. 常见坑速查

- **按 batch 1 的加速比做容量规划。** 高并发下加速比会衰减甚至变负，容量要按目标并发下的实测算。
- **只看接受率，不看草稿成本。** MATH500 的例子证明：首位置接受率 89% 也能慢于基线，c 过大时一切白搭。
- **跨引擎比较接受率。** 同一模型、同一草稿、同一数据集、同一解码设置，在 vLLM 与 SpecForge 上测出的接受率与均值接受长度可以朝相反方向偏（Qwen3-32B + EAGLE-3、GSM8K、贪心：vLLM 55.08%/2.65，SpecForge 约 44%/2.32；换 Qwen3-0.6B 独立草稿则顺序反转）。接受率是“某引擎计数器的读数”，不是草稿本身的属性。
- **换目标精度不重训草稿头。** fp16 头用于 int4 目标，特征漂移会悄悄吃掉接受率。
- **把“分布相同”理解成“字节相同”。** 评估、回归测试与缓存键设计都要按“统计等价”来做，否则一次引擎升级就会误报为模型退化。
- **树越宽越好。** 树宽的收益递减、成本线性增长；链式草稿在多数生产负载下比宽树更稳健（Berkeley 的 SpecDecode-Bench 对照：batch 64 时 21 token 宽树在所有负载下低于 1 倍，而 3 token 链仍保持加速）。

## 六、给 Patrick 的实用启示

1. **如果你只是用 ChatGPT / Claude / Codex 这类产品，推测解码与你的关系只有一个词：延迟。** 它不会让回答变对、变错或变便宜（token 计费口径不变），但能让长回答“出字更快”。感觉“变快了”时，先确认是不是推测、缓存或路由变了，再归因到模型本身。
2. **如果你想亲手验证一次（最小可行路线）：** 找一个有公开 EAGLE-3 头的开源模型（如 Qwen、Llama 家族），在 vLLM 或 SGLang 里开推测，先在自己的提示词上跑逐位置接受率曲线，再扫 γ=1、3、5、7，看加速比在哪里见顶、哪里跌破 1。这一组曲线跑完，你对“推测何时赚钱、何时亏钱”就有了一手体感，比背 6.5 倍这个数字有用得多。
3. **把今天的技术与前两天的报告连起来看：** 11 月 1 日的 MoE 讲的是“权重显存按总量算、算力按激活量算”；今天讲的是“解码延迟按权重扫掠次数算”。两者合起来才是推理成本的完整账本：MoE 决定了每次扫掠要搬多少权重，推测决定了搬一次权重能产出几个 token；而 11 月 2 日的 GRPO 讲的是“训练时如何用更少的采样换更好的策略”——训练、推理、部署三处的“省”，省的根本不是同一种东西，不要互相套用。
4. **工作中判断供应商说法的标尺：** 听到“我们用了推测解码、快 3 倍”，追问四件事——在什么 batch 下测的？在什么任务与温度下测的？草稿是什么、成本比 c 是多少？接受率与均值接受长度分别是多少？答不上这四件，加速比只是营销数字。

## 八、明天可继续的技术方向

- 把今天的清单落到一次真实测算上：给定一个开源目标模型与公开 EAGLE-3 头，跑逐位置接受率曲线与 γ 扫掠，看加速比在自己的提示词上何时见顶、何时跌破 1。
- Saguaro 的异步推测：草稿与验证解耦到不同硬件后，同步等待的消除能在多大 batch 下仍然成立，b* 阈值如何随硬件变化。
- 推测与前缀缓存、KV 缓存压缩的相互作用：长上下文下，注意力项随 M 放大的具体拐点在哪里；MoE 的专家共享率如何改变树宽的最优值。
- 原生多 token 预测（MTP）与外挂 EAGLE 头的对照：训练时就预测多个 token 的模型，在接受率与训练成本上是否真的优于事后加头。
- 结合 11 月 2 日的 HarnessMM 与 Routed Continual Learning：Agent 的工具循环里，多少 token 是“本来就可预测的模板与重复调用”，推测解码与“少调一次 LLM”这两类省法能否叠加。

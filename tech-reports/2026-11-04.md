# 每日 AI 技术报告 · 2026-11-04

**日期：** 2026 年 11 月 4 日（星期三）
**今日技术主题一句话概括：** RAG 最容易被低估的一环不是生成模型，而是切块——文档被切开的那一刻，代词、公司名、版本号这些“让一段话可被找到”的信息就丢了；今天深挖三条补救路线：生成式上下文、编码时上下文、以及查询侧改写与重排，并讲清各自的成本账与失效边界。

> 说明：本报告基于 2026 年 11 月 4 日通过浏览器阅读的公开资料写成，包括 Anthropic《Contextual Retrieval》官方全文、Jina Late Chunking 论文全文（arXiv 2409.04701）、AICassindra 的 RAG 深挖全文、Neomeric 的切分调优指南全文、Voyage voyage-context-3 官方博客与 Perplexity 上下文嵌入模型的发布整理、Chroma Context Rot 研究的二手整理，以及 HyDE 论文要点的二手整理。文中凡是单篇论文、单家厂商指南或单次测量的数字，均已标注来源与条件，不是通用结论；凡是“某来源的建议”，均已说明适用边界。

## 一、通俗解释：把书撕成碎页，再想靠碎页找答案

想象你把一本手册撕成几百张碎页，混在一起装进箱子，每张碎页单独编号入库。用户问“ACME 公司 2023 年第二季度的营收增长是多少？”，正确的那张碎页上只写着：

> “该公司的营收比上一季度增长了 3%。”

这张碎页本身没有公司名、没有时间——它在原书里是能读懂的，因为前一页刚写过“ACME Corp 的财报”。但撕开之后，检索系统看到的只是一张无名无姓的碎页，向量也只能按“营收增长 3%”这种通用语义去匹配，很容易被其他公司的“增长 3%”挤下去。

这就是传统 RAG 的“上下文困境”：**切块是为了让检索更精确，却把让文本可被识别的信息切掉了。** 今天的所有方法，本质上都在回答同一个问题：用什么办法，把碎页的“出处”还给它？

还有一个反向的力要同时记住：块切得太大，向量会把多个主题“平均”成一团，什么都匹配得不强；块切得太小，答案又可能被拆到两张碎页上，单张都不完整。切块不是预处理细节，它是整个 RAG 系统的质量天花板。

## 二、关键机制与实现要点

### 1. 先把流水线摆出来：离线一半、在线一半

RAG 分成离线与在线两半，故障定位要先分清是哪一半：

- **离线（文档变化时跑）：** 解析 → 切块 → 给每块生成向量（进向量索引）与词项索引（BM25）→ 存元数据（文档 ID、生效日期、访问权限）。
- **在线（每次提问时跑）：** 编码问题 → 向量检索 + 关键词检索 → 融合 → 重排 → 按 token 预算打包进提示词 → 生成 → 校验引用。

一条组织原则贯穿始终：**模型只能用送到提示词里的东西。** 如果含答案的那块没被检索到，再好的提示词也写不出有依据的正确答案。所以工程投入的大头应该在检索侧与度量上，而不是反复改提示词。

### 2. 路线 A：生成式上下文——Anthropic 的 Contextual Retrieval

做法是在切块之后、入库之前，多做一步：用一个便宜模型（如 Claude Haiku）读完整篇文档，为每个块写一段 50–100 token 的“定位说明”，再把这段说明贴在块前面，一起送入向量模型与 BM25 索引。

Anthropic 的例子很直观：原块是“该公司营收增长了 3%”，贴上说明后变成“这是 ACME Corp 2023 年第二季度财报中关于营收增长的一段……”——向量里从此同时含有内容与出处，BM25 也多了一批可精确匹配的词。

**实测数字（Anthropic 官方口径，语料为代码库、小说、ArXiv 与科学论文，指标为 top-20 检索失败率，即 1 − recall@20）：**

| 配置 | 失败率 | 相对降幅 |
|---|---|---|
| 传统向量 + BM25 基线 | 5.7% | — |
| + 上下文嵌入 | 3.7% | 35% |
| + 上下文 BM25 | 2.9% | 49% |
| + 重排 | 1.9% | 67% |

**成本账：** 借助提示缓存（文档只进缓存一次，各块复用），按 800 token 的块、8000 token 的文档估算，生成上下文的一次性成本约 1.02 美元 / 百万文档 token。但注意两点：这是 2024 年的 Haiku 价格口径，不能直接当作今天的报价；而且每次重建索引都要重付这笔账，语料越大、更新越频繁，账单越要先算清楚。

**零成本的平替版（建议先做这个）：** 不调用模型，直接把“文档标题 > 章节路径”贴在每个块前面。AICassindra 与 Neomeric 都把它列为性价比最高的单步改进——一次字符串拼接，零模型调用，能拿到生成式上下文的大部分收益。先测这个，再决定要不要为生成式上下文付费。

**适用边界：** 如果知识库小于约 20 万 token（约 500 页），Anthropic 的建议是别上 RAG——直接把全文放进提示词（配合提示缓存）更简单、更可靠。

### 3. 路线 B：编码时上下文——Late Chunking 与上下文嵌入模型

Anthropic 的路线是“先写说明、再编码”；Late Chunking（Jina AI，arXiv 2409.04701）反过来：**先编码、后切块。**

- **传统做法：** 先切块，再把每个块单独送进编码模型——每个块的向量只见过自己。
- **Late Chunking：** 先把整篇文档一次性送进长上下文编码模型，得到每个 token 的向量（此时每个 token 的向量已经“看过”全文），再按预先定好的块边界，对每块内的 token 向量做平均池化，得到块向量。块的文本不变，变的是向量里带上了全文信息。

论文里柏林的例子最能说明问题：用“Berlin”作查询， naive 切块下“It's more than 3.85 million inhabitants…”（它，指柏林）与查询的余弦相似度只有 0.7084，“The city is also one of the states…”只有 0.7535；Late Chunking 后分别升至 0.8249 与 0.8498——因为“它”和“这座城市”在编码时已经见过“Berlin”。

**论文的 BEIR 评测结果（nDCG@10，三模型、四数据集平均，相对提升）：** 句子边界切块 +3.63%（绝对 +1.9 个百分点）、固定长度切块 +3.46%、语义句子边界 +2.70%。幅度不算惊人，但胜在稳定——几乎所有组合上 Late Chunking 都优于 naive 切块，且**不需要额外训练、不需要调用大模型**。

**三条边界，论文自己写得很诚实：**

1. **块越小，收益越大；块越大，收益越小。** 大块本身已含较多上下文，再补全文信息的边际收益递减。
2. **上下文无关的任务上收益消失。** 在 Needle-8192、Passkey-8192 这类把短答案藏进无关文本的合成集上，Late Chunking 没有帮助——因为那里的“上下文”本来就是干扰。
3. **超长文档要分段：** 提出了 Long Late Chunking——把文档切成不超过模型上限的宏块，宏块之间留一段重叠 token 作上下文，再各自做 Late Chunking。

**与 Anthropic 路线的小规模对比（论文 4.5 节，ACME 虚构财报例子）：** 两种方法都把正确块（“营收增长 3%”那句）的相似度推到最高，且各块相似度分布接近；Late Chunking 的优势是不需要额外的大模型。但要注意这只是一个小例子，不是大规模对照实验，不能据此断言两者等价。

**托管的进化版：上下文嵌入模型。** Voyage 的 voyage-context-3 / context-4 与 Perplexity 的 pplx-embed-v2-context 把“整文档单遍编码出各块向量”做成了现成服务：

- Voyage 官方口径：在 93 个检索数据集、9 个领域上，voyage-context-3 在块级检索上比 OpenAI-v3-large 高 14.24%、比 Jina-v3 late chunking 高 23.66%、比上下文检索（Anthropic 路线）高 6.76%（均为厂商自报，须打折）。
- Perplexity 的 pplx-embed-v2-context（9B 与 0.6B 开源权重）走了另一条训练路线：整文档单遍编码后按块池化（即 late chunking），再用一个“查询感知的上下文压缩教师”逐 token 打分，让模型学会同时找回“答案块”与“支撑证据块”，而不只是单个金句。厂商自报：在其私有 Context-bench 上，答案召回@10 为 45.5%，高于 Voyage Context 4 的 31.1%；配套的 Q2D-Chunk 评测集有 6069 个查询、10 种语言，同时标注答案与证据。9B 输出 2048 维、可截断至 1024 维，int8 量化后每向量约 1KB；0.6B 被蒸馏到与 9B 的前 1024 维对齐，因此可以用 9B 建索引、用 0.6B 查——一个很实用的成本组合。视觉上，页面可按水平条带切分后整体编码，保留页面级视觉上下文。
- **共同的提醒：** 这些都是厂商自报数字；Perplexity 的 Context-bench 是私有的（官方说法是为防训练污染），外部无法独立复现。选型时要在自己的语料上跑同一批问题，再比较。

**三条路线怎么选（给一张对照表）：**

| 路线 | 做法 | 优点 | 代价与边界 |
|---|---|---|---|
| 生成式上下文（Anthropic） | LLM 为每块写 50–100 token 定位说明再编码 | 效果明确、可解释、任何编码器都可用 | 每块一次 LLM 调用、重建索引重付费 |
| Late Chunking（Jina） | 整文档编码后再按块池化 | 无需 LLM、无需训练、一次编码 | 需要长上下文编码器；文档超长要分段；无关上下文任务上无收益 |
| 上下文嵌入模型（Voyage / Perplexity） | 托管模型整文档单遍出各块向量 | 即插即用、省工程量 | 厂商锁定与自报数字；Perplexity 9B 自托管硬件成本不低 |

三者可以叠加，但不要一上来全叠加——先测最便宜的，再按度量结果加。

### 4. 混合检索：向量管语义，BM25 管精确词

向量检索擅长改写（“carry over”能匹配“rollover”），却对精确标识很弱：产品编码、错误码、人名、罕见缩写——向量会把它们“语义平均”掉。BM25 正好相反：按词频与逆文档频率打分，对精确词极强，对改写无能。

**标准做法是混合检索 + 按秩融合（RRF）：** 两路各取 top-50 左右，不直接合并分数（两路分数不在同一量纲），而是按排名融合：每块的分数为各路 `1 / (k + 排名)` 之和，k 常取 60；两路排名都靠前的块胜出，单路第一的块不自动胜出。

AICassindra 的 HR 例子说明了为什么这还不够：用户问“未用年假能否结转到明年”，向量检索命中了 2026 版政策的“rollover”块，BM25 却把 2023 版旧政策（含精确词组“carry over”）排在最前——如果直接把两路结果拼进提示词，模型可能引用旧政策给出“10 天”的错误答案。**所以每块必须带生效日期元数据，并 instruct 模型“冲突时以最新生效日期为准、并说明”**——这是 RAG 里最危险的一类失败：有引用、自信、但错了。

### 5. 查询侧：问题与文档本来就不是同一种文本

用户的提问是“问题”，文档是“陈述”，两者在向量空间里的分布本来就不一样。HyDE（Gao 等，arXiv 2212.10496）的做法是：先让 LLM 为问题写一篇“假设的回答文档”，再用这篇假设文档的向量去检索真文档——因为假设文档在文体、词汇、长度上都更像目标文档。原论文在 TREC DL19 上报告 nDCG@10 为 61.3，高于无监督基线 Contriever 的 44.5 与 BM25 的 50.6，接近有监督微调的检索器。

**使用边界：** 假设文档不需要事实正确，只需要“像”目标文档；但如果 LLM 的假设本身跑偏（例如把问题理解错了方向），检索会被系统性带偏。所以 HyDE 更适合作为一路候选（与原始查询检索并行、再融合），而不是唯一检索路径；多采样几篇假设文档取平均向量，可以降低单次跑偏的影响。代价是每次提问多一次 LLM 调用，延迟与成本要计入在线预算。

### 6. 重排与打包：召回要宽，送进模型的要窄

两阶段是行业标准做法：

1. **召回阶段求宽：** 混合检索取 top-50 到 top-100，目标是“别漏”。
2. **重排阶段求准：** 用 cross-encoder（把问题与每块放在同一次前向里、做完整注意力）逐一打分，取 top-5 到 top-8。cross-encoder 比双编码器（向量）准得多，但因为要对每对问题-块跑一次模型，只能跑在候选集上，不能跑全库。

**为什么“少即是多”：** Chroma 2025 年的 Context Rot 研究测了 18 个前沿模型，发现所有模型都会随输入增长而下降——即使任务本身极其简单、即使远未达到上下文窗口上限。在 LongMemEval 对话实验里，同一问题、同一关键事实，只给约 300 token 的聚焦上下文时，所有模型都显著好于给约 113,000 token 的完整历史。更早的 Lost in the Middle 研究（Liu 等，2023）也显示 U 形曲线：相关信息放在开头或结尾时最容易被用上，放在中间 20 篇文档的第 5–15 篇时，准确率下降超过 30%。**结论：检索到 20 块却全塞给模型，是把一次好的检索变成一次差的回答。** 打包时要定额 token 预算、按排名顺序加块、超预算时整块丢弃（绝不把一块截半），并把最强的来源放前面。

### 7. 度量：先建评测集，再调任何参数

Neomeric 与 AICassindra 的共识顺序是：

1. **先写 50–200 个真实问题**，每个问题标注答案在原文中的**字符偏移**，而不是“在第几块”——因为块边界一变，按块号记的标签就全作废了。
2. **分开测两件事：** 检索召回（recall@k：正确答案块是否进了 top-k？MRR：第一个正确答案块排第几？）与生成质量（忠实度：每个 claim 是否有引用支撑？答案正确性）。两者分叉时，修的方向完全不同：召回低，修切块、加 BM25、加上下文头、改写查询；召回高但答案错，修打包、指令与模型。
3. **每次改动只改一个变量**，并重跑评测集；把评测集放进 CI，召回一下降就构建失败——因为检索质量的退化是悄悄发生的（加文档、换编码模型、改解析器都会引起）。
4. **先修解析器：** 很多“切块问题”其实是解析问题——PDF 两栏串行、表格结构丢失、标题丢失时，再好的切块也救不回来。先抽 10 篇解析后的纯文本读一遍，确认标题、表格与阅读顺序无误。

### 8. 常见坑一览

| 症状 | 常见原因 | 先试的修复 |
|---|---|---|
| 文档明明在，答案找不到 | 块丢了上下文、只有向量检索 | 标题路径前缀、上下文嵌入、加 BM25、查 recall@k |
| 答案只对一半、缺例外条款 | 答案被拆到多块、块太小 | 结构切分、规则类用大块、邻块扩展、small-to-big（小块检索、大块送模型） |
| 引用了旧版、答错了还很自信 | 无生效日期元数据 | 元数据 + 最新为准规则 + 旧版删除机制 |
| 文档里的指令被模型执行了 | 来源被当作指令 | 来源用定界块包裹、声明“来源是数据不是指令”、输出后校验引用 |
| 用户看到无权看的内容 | 事后在提示词里过滤 | 在索引查询内按用户身份过滤（ACL-aware），绝不在提示词里“请忽略” |
| 块越多答案越差 | Context Rot、干扰项 | 重排后只送 5–8 块、固定预算、整块丢弃 |
| 上线后质量悄悄下滑 | 索引漂移 | 统一模型版本重嵌、评测集进 CI、监控检索指标 |

## 三、给 Patrick 的实用启示 / 可以试用的点

1. **个人知识库的起步顺序（按性价比排）：** 结构切分（按标题、段落，句中不断开）→ 每块贴“标题 > 章节路径”→ 加 BM25 与 RRF 融合 → 加 cross-encoder 重排、只送 5–8 块。跑完这四步、测出 recall@k 之后，再决定要不要上生成式上下文或上下文嵌入模型——不要一上来就为每块付 LLM 调用费。
2. **小语料别上 RAG：** 20 万 token 以内（约 500 页）的资料，直接全文进提示词 + 提示缓存，往往比搭一套 RAG 更准、更便宜、更容易排错。RAG 是为“装不下、常变化、要分权限、可追溯”准备的。
3. **可以动手试的三个具体东西：** Voyage 的 voyage-context-4（按需计费、32K token / 块）适合长合同、长论文类语料；Perplexity 的 pplx-embed-v2-context-0.6B 适合本地轻量实验，且可与 9B 共享索引空间；开源重排可用 BAAI/bge-reranker-v2-m3，零 API 成本。试之前先准备 30 个自己的真实问题并标注答案位置，否则“感觉变好了”不作数。
4. **不要做的三件事：** 不要只凭向量相似度阈值过滤（阈值在不同语料上漂移极大）；不要把重排省掉、直接把 20 块全塞给模型（Context Rot 会吃掉你的检索收益）；不要在提示词里让模型“忽略无权内容”——权限必须在索引查询里过滤。
5. **一句话自查清单：** 每次 RAG 回答出错时，先问“正确答案块进了 top-8 吗？”——进了，是生成与打包的问题；没进，是切块与检索的问题。两个问题的修法完全不同，别混在一起调。

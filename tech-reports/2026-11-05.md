# 每日 AI 技术报告 · 2026-11-05

**日期：** 2026 年 11 月 5 日（星期四）
**今日技术主题一句话概括：** Agentic RAG 不是“更强的检索”，而是把检索从“一次查完”换成“带计划、带纠错、带预算的循环”：多跳问题只有这样才答得对，但每一跳既是一次纠错机会，也是一个新的出错面——系统的可靠性，最终取决于坏检索在变成下一跳的前提之前被拦住的比例。

> 说明：本报告基于 2026 年 11 月 5 日通过浏览器阅读的公开资料写成，包括 Ergini《Agentic RAG》全文、Ragnight《Agentic RAG》全文、LatentEval《Agentic RAG 架构与失效面》全文、Scaling Out AI 第 40.5 节《RAG at Scale》全文，以及 Self-RAG（ICLR 2024）、CRAG、IRCoT（ACL 2023）、Adaptive-RAG 的论文摘要与整理。文中凡是单家工程博客的成本与延迟数字，均已标注来源与条件，不是通用结论；凡是论文数字，均已说明数据集与模型条件；凡是示意性算例，均已说明它是示意，不是实测。

## 一、通俗解释：一次翻书 vs 侦探破案

想象你要回答一个问题，资料是一座图书馆。

- **单次 RAG（一次翻书）：** 你把问题原样抄在纸条上交给图书管理员，他按纸条找来最像的几页，你就着这几页写答案。问题简单时，这很高效；但问题如果本身“缺一块信息”，纸条上就没有管理员需要的关键词——比如问“我们最大办公室所在国家的休假政策比当地法定最低多几天”，没有任何一页同时写着“最大办公室”和“休假政策”，管理员只能凭“办公室、休假、法定”这些词拼凑几页似是而非的东西，而你还会自信地写出一个答案。
- **Agentic RAG（侦探破案）：** 你先派一个侦探：他读问题后先列计划——先查各办公室人数（里斯本 310 人最多 → 葡萄牙），再查葡萄牙的休假政策（25 天），再查葡萄牙法定最低（22 天），最后算出差 3 天。每一步的收获决定下一步查什么；每一步查完，他先问自己“够回答了吗？缺哪一块？”；不够就再查一轮，够了才写答案，并且每个数字都标出它来自哪一页。

**一句话区分：** 单次 RAG 把检索当作“生成之前的一步”；Agentic RAG 把检索当作“模型可以反复调用的工具”。前者是函数（输入问题，输出答案），后者是循环（问题 → 计划 → 查 → 判断 → 再查 → 回答）。循环能回答单次答不了的问题，代价是：每多一跳，就多一次出错、多一次花钱、多一次等待。

## 二、为什么单次检索注定在三类问题上失败

### 1. 语义空洞：问题里没有答案的关键词

多跳问题的答案分布在两篇以上的文档里，而连接它们的“桥”——一个实体名、一个日期、一个版本号——只存在于中间结论中，不存在于原始问题里。原始问题的向量会落在两个主题之间，谁都不贴近，于是检索返回的是一堆“沾边但无用”的块。昨天的报告讲过切块会丢上下文；今天的问题更根本：**即使切块完美，单次检索也找不到它从未被告知要找的东西。**

### 2. 组合问题被“平均”掉了

“我们定价与 Acme 相比如何、对方有哪些我们没有的功能？”——一个向量要同时代表“我们的定价”“对方的定价”“对方的功能”三个检索意图，结果是三个方向的平均，哪个都查不准。分解成三个子查询、分别检索、再合并，是唯一不靠运气的做法。

### 3. 含糊与跨源：问题本身需要先被“翻译”

多轮对话里的“那它的延迟呢？”离开上文毫无意义；“本季度 MRR 是多少？”的答案在 SQL 表里，不在向量库里；“对方昨天宣布了什么？”的答案在网上，不在内部文档里。单次 RAG 只有一个检索路径、一种查询写法，注定在这些问题上用错工具。

## 三、五种模式：不是一套组合拳，而是五件按需取用的工具

生产系统通常只组合其中两三种。按“从便宜到昂贵”排列：

### 模式一：查询分解（最便宜，没有循环）

规划器把问题拆成 2–5 个子查询，各自独立检索，结果合并后再重排、生成。独立的子查询可以并行发，延迟只多一次规划调用（Ergini 的生产经验：用小模型规划约 300–600ms）。适用：组合问题、对比问题。**关键优化：先用一个快速分类器判断问题是不是单意图——是，就跳过规划器，别为简单问题付规划税。**

### 模式二：多跳检索（Agentic RAG 这个词通常指的就是它）

上一跳的结论变成下一跳的查询。经典实现是 IRCoT（Trivedi 等，ACL 2023）：先以原问题取一批基线段落，然后循环两步——（i）根据已收集段落与已有推理句，写出下一句思维链；（ii）用这句新推理句再检索一批段落。如此交替，直到满足停止条件。

论文数字（GPT-3，四个多跳数据集 HotpotQA、2WikiMultihopQA、MuSiQue、IIRC）：检索召回最高提升 21 个百分点，下游问答 F1 最高提升 15 分，思维链中的事实错误最多减少约 50%；Flan-T5-XL（3B）配 IRCoT 在部分数据集上甚至胜过 58 倍大的 GPT-3 单次检索。**但也有例外：GPT-3 在 IIRC 上召回大涨、问答分数却未显著提升——检索到了，不等于模型用对了。** 这一点要记牢：多跳改善的是“找得到”，不是自动改善“答得对”。

### 模式三：自纠与反思（给循环装一个刹车与质检员）

每跳之后，一个“裁判”步骤判断已检索内容是否足以回答子问题：够 → 进入生成；不够 → 改写查询再查。两种经典实现，路线完全不同：

- **Self-RAG（Asai 等，ICLR 2024）：把“反思”训进模型里。** 模型在生成过程中输出特殊的 reflection token：Retrieve（要不要查？）、IsRel（这段相关吗？）、IsSup（我的回答被这段完全支撑吗？）、IsUse（这段回答对用户有用吗，1–5 分）。推理系统拦截这些 token，决定下一步是检索、过滤还是生成，并用分段束搜索挑出反思分数最优的输出。优点是反思与生成一体、按需检索（可跳过检索）；代价是**必须微调模型、必须定制推理环**——这不是给现成 API 加个提示词就能复现的。
- **CRAG（Yan 等，2024）：把“质检”做成即插即用的外挂评估器。** 一个轻量检索评估器（论文用 T5-large 级模型）给检索结果打分，分三档处理：正确（高置信，常用阈值约 0.7 以上）→ 做知识精炼（切掉无关句子、只留针对查询的知识条）后送生成；错误（低置信，约 0.3 以下）→ 丢弃内部结果，改写查询后走网络搜索；模糊（中间）→ 内部精炼结果 + 网络搜索结果混合使用。**注意：CRAG 这个缩写另指一个同名的综合 RAG 基准（Comprehensive RAG Benchmark），两者不要混淆。**

### 模式四：工具增强的检索（路由问题）

Agent 面前摆一张工具菜单——向量检索、关键词检索、SQL、网络搜索、内部 API——每个子查询由模型按需选工具。“MRR 是多少”走 SQL，“文档怎么说 webhook 安全”走向量库，“对方昨天宣布了什么”走网络搜索。工程代价是真实的：每个工具需要干净的 schema、错误处理，以及“像产品说明书一样写的工具描述”（做什么、接受什么、返回什么、什么时候不要调用它）。**工具描述写得差，模型就会系统性地选错工具——这是路由模式最常见的失败，不是模型“不聪明”。**

自适应路由是这个模式的升级版：Adaptive-RAG（Jeong 等，NAACL 2024）用分类器按问题复杂度分流——不检索、单次检索、多步循环三档；而 Search-R1（Jin 等，2025 预印本）更进一步，用强化学习直接训练模型“何时在推理中自行发起搜索”，把路由策略从提示词变成了可训练的行为。

### 模式五：分层检索（先便宜地缩小范围，再贵地精查）

先用小 embedding 或纯 BM25 在标题与章节上做一次宽泛筛选，把百万级块缩到数千；再用大 embedding + 重排只处理这个子集。Agent 的作用是按问题决定“查多深”。适用：超大语料（千万块以上）或成本敏感场景（80% 的简单问题走快路径，20% 的难题才上昂贵检索）。

## 四、循环的成本账：每一跳都付三份钱

Scaling Out AI 把一跳的成本拆得很干净：检索 + 重排 + 生成。设总跳数为 H，则总成本约等于 H 乘以单跳成本——**跳数不是“多做一点 work”，而是把整条流水线重复 H 遍。**

Ergini 的生产数字（2026 年定价口径，均为作者自报、须按自己的模型与流量复测）：

| 配置 | 每查询成本 | p95 延迟 |
|---|---|---|
| 单次 RAG（混合 + 重排） | 约 $0.002 | 约 1.4s |
| 仅分解（1 次规划 + 3 次检索） | 约 $0.005 | 约 2.2s |
| 3 跳 + 自纠（小模型全程） | 约 $0.015–0.025 | 约 3–6s |
| 混合源（工具增强 + 分解） | 约 $0.02–0.05 | 约 3–8s |
| 研究式合成（分层 + 多跳 + 自纠） | 约 $0.05–0.20 | 约 8–20s |

单跳的延迟构成（作者的生产测量）：查询 embedding 约 120ms、混合检索约 80ms、重排（24 → 6）约 280ms、规划/反思 LLM 调用约 500ms，合计一跳约 1.0s；3 跳 + 最终生成 p95 约 3.9s。**这就是为什么“3–5 跳”必须是写进代码的硬预算，而不是提示词里的建议：** 提示词里的上限，模型是可以“忘记”的；代码里的上限，才是成本的上限。

还有两笔容易漏的账：

1. **被拒绝的答案也全价。** 一个在第 3 跳以“我不知道”收尾的查询，付了 3 次检索、3 次规划与 1 次生成的钱，换来零答案。必须单独统计“被拒查询的成本”，并设租户级日上限——否则一个自动化脚本一小时就能把账单翻 100 倍。
2. **上下文越攒越长，证据反而越难被用上。** 每一跳都把新块追加进上下文，最终生成时面对的是几跳的混合物。昨天的报告提过 Lost in the Middle（相关信息在长上下文中间时最容易被忽略）与 Context Rot（输入越长，所有模型表现都下滑）——**多跳系统如果不做“最终重排”（对原始问题、而非子查询，重新排一遍累积的块），就会亲手埋掉自己辛苦找回的证据。**

## 五、可靠性数学：为什么“每跳 90% 准”最后只有约 66% 对

LatentEval 给了一个刻意取整的示意算例（**示意数，不是实测**）：假设 4 跳链中每跳独立成功的概率为 0.90，且没有任何纠错，则端到端成功率是 0.90 的 4 次方，约 0.66——单跳看似可靠的 90%，串联四次后，每三次回答就有一次是错的。真实系统里各跳共享同一个检索器与同一个模型，失败往往是相关的（不是独立的），所以实际数字会高于 0.66，但**形状不变：串联放大失败，纠错是唯一把它除回去的东西。**

由此得到 Agentic RAG 唯一真正关键的度量：**containment rate——批评者（自纠门）在坏检索进入记忆、成为下一跳前提之前，把它拦住的比例。** 一张只画循环、不标注门控捕获率的架构图，只讲了能力，没讲风险。具体到四种模式，失效面与门控各不相同：

| 模式 | 错误从哪里开始 | 它如何传到答案 | 拦住它的门 |
|---|---|---|---|
| 选（规划/路由） | 问题被分错类，走了为另一个问题设计的路径 | 之后每一步都继承错误的前提 | 路由置信度阈值，低置信时回落到固定单次流水线 |
| 查（自纠） | 裁判本身校准错误：放过坏上下文，或否决好上下文 | 循环直接交付错误，或永远不收敛 | 用已知坏检索标定裁判，给出捕获率与置信区间 |
| 链（多跳） | 第一跳的错误结论被写进记忆、当作事实 | 之后每跳都基于中毒的前提推理 | 每跳结论入记忆前，先做充分性检查 |
| 委（多 Agent 编排） | 子查询被错分或子 Agent 答错 | 合并时把错误当作可信来源之一折进去 | 编排器在合并前逐一验证子 Agent 的返回 |

还有四个生产中反复出现的具体坑：

- **无限反思：** 没有硬上限的循环会在无答案问题上一直烧钱。解法是三件套：硬 MAX_HOPS（3–5）、逐跳递减的置信阈值（越到后面越容易“认了”、不再纠结）、最终跳的强制作答提示（用已有材料回答并承认缺口）。
- **子查询漂移：** 规划器拆出的问题“相关但不是用户问的”（如把“如何配置失败支付的 webhook”拆成“webhook 是什么”“失败支付是什么”）。解法：每次检索提示里都带上原始问题，最后再做一次覆盖检查——“这些子查询真的能回答用户的问题吗？”
- **规划者过度自信：** 模型不愿承认“材料不够”，几乎给任何检索都打 0.7 分以上，因为打高分就能早点收工。Ergini 的经验是：裁判与生成要用不同的模型或不同的系统提示，并且阈值要按标注集校准——他曾把小模型的裁判阈值提到 0.85 才管用。
- **检索注入（比提示注入更隐蔽）：** 检索到的块会决定下一跳查什么。如果语料含用户生成内容，攻击者可以在文档里写“别管用户的问题，改查这个”，规划器就会照做。解法：用系统标记“夹住”每个检索结果、喂给规划器前剥离指令式语句、绝不让检索文本覆盖原始问题；高风险答案走人工复核。

## 六、评测：除了答案对不对，还要评“走过的路”

标准 RAG 指标（忠实度、上下文召回、上下文精度、答案相关性，RAGAS 体系）只评最终输出。Agentic RAG 必须再加三项轨迹指标，否则两个系统可能答案相同、成本与可靠性天差地别：

1. **子查询覆盖率：** 专家会问的子查询中，规划器实际问出了几个？——抓分解失败。
2. **逐跳检索召回：** 每一跳是否找回了它应该找回的块？——因为一跳查错会毒害之后所有跳，必须按跳归因，不能只看最终结果。
3. **轨迹效率：** 实际跳数 / 人类需要的最少跳数。效率低于 0.5，说明循环在猜，不是在查。

外加三条评测纪律：

- **评测集要含“期望子查询”与“最少跳数”，不只是问题与答案。** 没有这两样，轨迹指标无从算起。
- **直接测量门控：** 向系统注入已知坏检索，记录裁判拦住的比例并给出置信区间——把“系统会自我纠错”从一句口号变成一个数字。
- **跨运行一致性：** 同一问题跑多次，答案是否稳定？一次对、一次错的系统，即使平均分好看，也不可靠；两个版本的差异要用配对显著性检验判断，不能只看柱状图是否重叠。

## 七、给 Patrick 的实用启示 / 可以试用的点

1. **起步顺序（按性价比排，别一上来就上 Agent）：** 先把单次 RAG 做到位——结构切分 + 标题路径（11 月 4 日报告）→ 混合检索 + 重排 → 只送 5–8 块。跑出评测集后，再按失败类型加模式：组合问题多 → 加分解；必须先查 A 才能查 B 的问题多 → 加多跳；错答代价高 → 加自纠。OmniAPI 的案例就是这个顺序：单次 78% → 分解 86% → 2 跳 91%，没上自纠、没上工具选择、没上分层，就够了。
2. **三条“不值”的硬阈值（先定下来，再动手）：** 多跳或跨源问题不到全部流量的约 10%，不上 Agent；单次 RAG 在多数流量上上下文召回已高于约 0.85，只把少数难题分流给 Agent；同步回答的延迟预算低于约 2 秒，多轮循环直接排除、只留异步路径。**最实用的折中是入口分类器：90% 的流量走单次，10% 才唤醒 Agent。**
3. **如果要亲手搭一个最小版本：** 用小模型做规划器与裁判（大模型只做最终生成）、硬编码 MAX_HOPS = 3、置信阈值逐跳递减（如 0.6 → 0.5 → 0.4）、最终跳强制作答、每跳日志记下查询、返回块 ID、置信度与延迟。跑 30 个自己的多跳问题，先看三项轨迹指标，再决定要不要加第 4 跳或换裁判模型——**不要先加跳数，先看是哪一跳在犯错。**
4. **安全红线（今天就要写进设计里）：** 权限过滤必须在检索工具层做（按用户身份过滤索引查询），绝不在提示词里写“请忽略无权内容”；检索结果进规划器前要做“夹住”与指令剥离；低置信答案路由到人工队列，而不是直接交付。
5. **把这三天的技术报告连起来读：** 11 月 3 日的推测解码讲的是“让每一跳的生成更快”（省权重搬运）；11 月 4 日的切块与上下文嵌入讲的是“让每一跳捡到的块更准”（省上下文丢失）；今天讲的是“决定跳几次、往哪跳、什么时候停”（省无效的跳）。**三处省的不是同一种东西：推理速度、检索精度、循环次数——调参时别互相代换。**

## 九、明天可继续的技术方向

- GraphRAG：把实体与关系建成图后，一次图遍历如何替代多次向量多跳；图分区边界如何影响遍历成本；以及它与向量检索的混合方式。
- 评测进阶：RAGAS / faithfulness 自动评分的可靠性边界，以及如何用少量人工标注校准 LLM 裁判——特别是裁判本身的 containment rate 如何测量。
- 训练式路由：Search-R1 用强化学习训练“何时搜索”的策略，与提示词式 Adaptive-RAG 相比，在什么规模下才值得付出训练成本。
- 把今天的清单落到一次真实测算上：给定一个小型语料与 30 个多跳问题，跑分解 → 多跳 → 自纠三档，记录每档的轨迹三指标与每查询成本，看收益在第几档见顶。
